# Процедуры финального ревью

## Быстрый список проверки

- уровень процесса по `docs/adr/0004-risk-tiered-development-workflow.md` и `docs/adr/0010-small-bugfix-fast-lane.md`;
- ясное прямое поручение для уровня 1, compact bugfix note для уровня `1B` либо область задачи Jira и критерии приёмки для уровней 2–3;
- план и пакет источников, если он требовался для этой задачи;
- полная фактическая разница и несвязанные изменения;
- целевые тесты, необходимые интеграционные проверки области, ключевой smoke-сценарий и контрольная перепроверка;
- соответствие требования доказательству;
- документы и ADR;
- русский язык артефактов;
- поиск секретов;
- факты о ветке, базовой ветке и PR;
- барьеры безопасности Telegram.

## Условные барьеры по уровню риска

- Для уровня 1 проверить язык, ссылки, форматирование, отсутствие секретов и точность описания изменения.
- Для уровня `1B` проверить compact bugfix note, воспроизведение или целевой тест, минимальный smoke, secret scan, рабочую ветку при изменении git и отсутствие признаков повышенного риска.
- Для уровня 2 проверить задачу Jira, `plan.md`, ветку задачи, целевые и необходимые интеграционные тесты, ключевой сценарий и `implementation-report.md`.
- Для уровня 3 дополнительно проверить `plan-source-context.md`, точный `Status: approved` в `plan-review.md`, принятый ADR при структурном или сквозном решении, `test-plan.md` при недостаточности автоматических тестов и специальные доменные проверки.
- Если обязательный барьер уровня риска нельзя доказать, `approved` запрещён.
- Если Telegram live gate не выполнен, `approved` уровня `1B` может означать только локальную готовность к PR; production-готовность должна быть явно оставлена незакрытой.

## Приоритет замечаний

- Критический — раскрытие секрета, неразрешённое разрушительное или внешнее изменение, потеря данных, обход авторизации.
- Существенный — критерий приёмки не закрыт, отсутствует обязательный тест или проверка ключевого сценария, неверна область задачи либо нарушен процесс.
- Незначительный — проблема поддерживаемости или ясности без нарушения результата.

Критическое или существенное замечание запрещает `approved`. Незначительные замечания могут сопровождать `approved`, если они явно необязательны.

## После `changes_requested`

После первого непройденного review роль `developer` одним циклом исправляет весь пакет замечаний и обновляет отчёт, затем допускается одна повторная проверка. После второго обе попытки сохраняются, создаётся `problem-escalation.md` и выполняется одно консолидированное исправление. Если следующий review снова не одобрен, работа останавливается для решения владельца. Полная регрессия продукта в этот цикл не входит.
