# Процедуры агента-разработчика

## Проверка задачи Jira

Для бага, функции, пользовательской истории, изменения runtime-поведения, workflow или процесса разработки сначала получить существующую задачу Jira `CB` или создать новую по постоянному намерению владельца. Затем прочитать описание, комментарии, связи, родительскую задачу или эпик, вложения, текущий статус и критерии приёмки. Блокирующие зависимости определять по связям Jira и фактическим статусам.

## Артефакты

Путь по умолчанию: `tasks/<ISSUE-KEY>/`.

- Compact bugfix note — `Симптом / Причина / Правка / Проверка / Риск` для
  уровня `1B` по ADR-0010. Может быть в Jira, PR, локальном `bugfix-note.md` или
  передаче результата.
- `plan.md` — что и почему меняется, что остаётся вне области задачи, риски и проверки.
- `plan-source-context.md` — реальные источники Jira и документов для задачи уровня 3, включая задачу с большим числом источников.
- `needs-info.md` — закрытый список вопросов и влияние отсутствующего ответа.
- `test-plan.md` — ручные сценарии, если автоматические тесты недостаточны.
- `implementation-report.md` — факты и доказательства, а не копия плана.

## Изменение статуса Jira

Перед каждым изменением статуса получить актуальные переходы конкретной задачи. Не переносить названия статусов из других проектов и не предполагать их наличие в `CB`.

В начале планирования уровня 2–3, до подготовки `plan.md`, при ясном намерении пользователя предложить доступный реальный переход, соответствующий логической стадии «Планирование» (`Planning`). Если такого перехода нет, продолжить без выдуманного статуса и точно зафиксировать фактическое состояние. Для уровня `1B` переходы `Planning` и `Ready` не обязательны.

Перед первым изменением кода снова получить актуальные переходы и при ясном намерении пользователя предложить доступный реальный переход, соответствующий логической стадии «В работе» (`In progress`). Подготовка ветки и публикация плана сами по себе не означают начало реализации.

## Публикация плана

Для уровня `1B` показать compact bugfix note. Для уровней 2–3 всегда показать пользователю `plan.md`. Показывать `plan-review.md` вместе с планом только тогда, когда независимое ревью требовалось по уровню риска. Публикация плана сама по себе не разрешает начинать реализацию или изменять Jira.

Для структурного или сквозного решения создать ADR со статусом `Предложено` и передать его на проверку вместе с планом. Проверяющий не принимает ADR. После успешной проверки показать ADR владельцу; начинать реализацию можно только после явного принятия владельцем и изменения статуса ADR на `Принято`.

## Подготовка Git

Проверить рабочее дерево, обновить `main` и создать или переименовать рабочую ветку в `task/<ISSUE-KEY>` до правок. Ветка задачи не должна оставаться локальной: после успешных проверок выбранного уровня риска выполнить commit, push, PR, дождаться CI/review и выполнить merge в `main`, если gate не заблокирован. Уровень `1B` ускоряет артефакты, но не разрешает ветку без ключа Jira.

## Проверка изменений Telegram

Использовать обезличенные тестовые данные, исключить реальные отправки, проверить повторные обновления, права, настройку `Privacy Mode`, ограничения частоты и повторные попытки. Для многопользовательских live-сценариев доступны профили `default` и `tg-test`; перед использованием выполнить безопасный `probe` каждого профиля через `C:\Users\User\.codex\tools\telegram.ps1` и фиксировать только ярлык профиля и обезличенный результат. Локальная готовность к PR может быть доказана output-driven тестом или fake Bot API. Production-готовность рабочего экземпляра требует deployment проверенного release и живой Telegram-проверки; несколько малых исправлений можно проверять пакетно на release acceptance, если отчёт честно фиксирует незакрытый live gate.

## Эскалация

После трёх попыток зафиксировать:

- проблему и воспроизведение;
- три попытки и результаты;
- вероятную причину;
- варианты и компромиссы;
- рекомендуемое решение;
- необходимое решение пользователя/техлида.

Три попытки выше относятся к одной технической проблеме. Для независимых review действует отдельный более ранний барьер: после первого непройденного review исправляется весь пакет замечаний; после второго обе попытки сохраняются в `reviews/<plan|final>/`, создаётся `problem-escalation.md` и выполняется одно консолидированное исправление. Если следующий review снова не одобрен, работа останавливается для решения владельца.

## Соразмерность MVP

Малый багфикс уровня `1B` завершается compact bugfix note, целевым тестом или воспроизведением, минимальным smoke, secret scan и короткой diff-проверкой. Обычная задача завершается целевыми тестами, необходимыми интеграционными проверками и smoke-сценарием своей области. Полная регрессия продукта проводится отдельно после готовности всего MVP. Планирование, проверки и review не должны превращаться в основную часть работы; ориентир накладных расходов — до 25% цикла обычной задачи и до 15% цикла уровня `1B`.

## Передача результата

Для уровня `1B` показать compact bugfix note и diff-вердикт. Для уровней 2–3 показать отчёт реализации и финальное ревью. Для задачной ветки выполнить маршрут commit → push → PR → CI/review → merge при успешных gates; если gate заблокирован, зафиксировать блокер в Jira. Точно перечислить, какие изменения Jira, Git и Telegram выполнены, а какие заблокированы.
