# CB-34 — отчёт о реализации

## Итог

После первого успешного одобрения анкеты участнику автоматически доставляется
сообщение «Регистрация подтверждена. Главное меню уже доступно.» с канонической
reply-клавиатурой. Ручной `/start` больше не нужен.

До одобрения меню не показывается: обязательная ручная модерация сохранена.

## Реализация

- переход `pending → active`, стартовый грант, аудит, update receipt и уникальное
  outbox-событие `registration.approved` фиксируются одной транзакцией;
- exact replay и повторное одобрение не создают второе событие;
- системное уведомление обходит quiet hours и планируется немедленно;
- worker повторно проверяет `member.status == active` перед каждой доставкой;
- Telegram sender использует allowlisted текст, а production composition
  прикрепляет `main_menu_markup()` только к `registration.approved`;
- временные ошибки Telegram проходят через существующую retry-политику worker.

## Критерии приёмки

| Критерий | Результат | Доказательство |
|---|---|---|
| Автоматическое меню после одобрения | пройден | Интеграционный registration-сценарий проверяет адресата, текст и 10 кнопок production-меню. |
| Подтверждение администратора сохраняется | пройден | Существующий callback-сценарий проходит без изменений. |
| Нет дубля от replay/повторного approval | пройден | Одна outbox-запись, один delivery после повторного update. |
| Надёжная доставка | пройден | Approval и outbox атомарны; worker выполняет bounded retry. |
| Немедленно вне quiet hours | пройден | Отдельный тест в 23:00 сохраняет `scheduled_at == now`. |
| Не отправлять inactive участнику | пройден | После materialization статус `paused` даёт `notification_obsolete`. |

## Остаточный риск

Доставка Telegram имеет стандартную гарантию at-least-once: падение worker после
успешного Bot API вызова, но до фиксации `sent`, теоретически может дать повторное
сообщение после истечения lease. Повторное одобрение или replay update дубль не
создают. Риск принят как неблокирующий и не меняет права доступа.
