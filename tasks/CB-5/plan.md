# CB-5 — план согласования кармы и видимости профилей

## Цель

Закрыть `Q-005`, `Q-006` и `Q-011` подтверждённым владельцем пакетом правил и
синхронизировать все канонические документы так, чтобы реализация `CB-12` не
требовала продуктовых догадок.

## Уровень процесса

Уровень 3: задача затрагивает приватность, ролевую авторизацию и несколько
источников требований. До реализации выполняется одно независимое review полного
планового пакета. Новый ADR не требуется: меняются продуктовые правила внутри
существующих границ ролей, модульного монолита и `D-005`.

## Подтверждённые решения

### Q-005 — право оценивать

- Оценка доступна после хотя бы одного assignment между парой в любом
  направлении со статусом `approved` или `partially_approved` и ненулевой
  выплатой.
- Community-task не создаёт личного взаимодействия с administrator/reviewer.
- `cancelled`, `rejected`, незавершённый dispute и `no_show` допуска не дают.
- Самооценка запрещена. Administrator не обходит правило для личной оценки.
- После первой валидной выплаты eligibility становится исторически необратимым
  фактом взаимодействия. Экономическая correction/reversal и изменение
  assignment в административной проекции его не аннулируют.
- Существующую оценку можно изменять, только пока оба участника `active`.

### Q-006 — комментарий

- Получатель и обычный moderator видят только агрегат и количество текущих
  оценок, без текста, автора, времени отдельной оценки и истории.
- Автор видит и редактирует свою текущую оценку и комментарий.
- Только active administrator с `karma_review` видит автора, комментарий и
  историю; каждый просмотр журналируется.

### Q-011 — профили

- Active member, moderator и administrator видят безопасные карточки всех
  active members.
- `pending`, `paused`, `restricted`, `suspended`, `left` и `banned` исключены из
  каталога и недоступны по прямому идентификатору другим обычным пользователям.
- Пользователь видит собственную карточку в `active` и `paused`; при `pending`,
  `restricted`, `suspended`, `left` и `banned` обычный профильный интерфейс её
  не открывает. Индивидуальные разрешения `restricted` остаются вне CB-5.
- Active administrator с `member_read` может читать карточки всех статусов, но
  не получает через карточку баланс, историю операций, Telegram ID, приватные
  комментарии кармы, страйки и административный аудит.
- Каталог, пагинация, callback и прямое открытие UUID используют одну policy;
  отказ не подтверждает существование скрытого профиля.

## Матрица доступа

| Actor | Safe active profile | Non-active foreign profile | Aggregate karma | Own vote/comment | Foreign raw karma/history |
|---|---:|---:|---:|---:|---:|
| active member | да | нет | да | да, при eligibility | нет |
| active moderator | да | нет | да | да, при eligibility | нет |
| active administrator | да | только с `member_read` | да | да, при eligibility | только с `karma_review`, с audit |
| paused member | только свой | нет | только свой | нет | нет |
| pending/restricted/suspended/left/banned | нет | нет | нет | нет | нет |

Все «да» означают серверную проверку актуального actor/target status. UI не
является границей безопасности.

## Последствия для CB-12

- Нужен единый профильный policy/service для list и get-by-id.
- Eligibility фиксируется durable-фактом первой валидной выплаты и после этого
  не пересчитывается назад из mutable projection, Telegram history или кэша.
- Karma mutation повторно проверяет actor/target status и eligibility в одной
  транзакции с текущей оценкой и append-only revision.
- Одновременные first vote/update сериализуются по паре `(author, recipient)`.
- Admin read raw karma создаёт audit event; user projection физически не содержит
  raw fields.
- Пагинация каталога не должна раскрывать или повторно показывать скрытые статусы
  при конкурентном status change; stale cursor безопасно перезапускается либо
  продолжает только по разрешённой projection.

## Риски и альтернативы

- «Оценивать любого active member» проще, но позволяет массовые оценки без
  подтверждённого контакта — отклонено для пилота.
- Показ обезличенного комментария полезнее как feedback, но легко раскрывает
  автора по контексту и стилю — отложен до отдельного модерируемого механизма.
- «Профиль только после взаимодействия» уменьшает видимость сообщества и требует
  сложной навигации — отклонено для закрытого пилота 20–30 человек.
- Если каталог станет чувствительным после пилота, видимость должна меняться
  отдельным датированным решением, а не скрытой настройкой runtime.

## Что не входит

Python-код, схема БД, миграции, seed, Telegram handlers и реализация `CB-12`.
Также не проектируются публичный веб-каталог, экспорт raw karma и публикация
анонимных комментариев.

## Проверка и завершение

Проверки определены в `test-plan.md`. После синхронизации создаётся
`implementation-report.md`, затем одно независимое final review всего diff.
Полная продуктовая регрессия не запускается: это документационная задача до
реализации CB-12.
