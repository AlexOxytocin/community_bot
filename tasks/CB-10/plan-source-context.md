# CB-10 — контекст источников плана

## Jira

- CB-10: «Реализовать создание задания и атомарное резервирование награды».
- Семь критериев приёмки: недостаточный баланс без частичного резерва; exact
  replay без второго задания; срок в прошлом; запрет автору принимать своё
  задание; точный возврат без опыта; восстановление черновика после перезапуска;
  конкурентные публикации без отрицательного баланса.
- Входящие блокеры CB-7 и CB-9 имеют статус `Готово`; CB-10 блокирует CB-11.
- Ветка `task/CB-10`, база `main` после CB-9:
  `5a174807cd5f3cec47920985dd73acdc211537d4`.

## Канонические решения

- Участник публикует задание только из точной активной версии фиксированного
  шаблона; input проверяется по её JSON Schema.
- Награда резервируется отдельно для каждого слота, поэтому полный резерв равен
  `credit_reward_per_performer * performer_slots`.
- Корректная отмена возвращает весь неиспользованный резерв и не даёт опыта.
- `origin=community` не имеет личного автора и резерва. Создание community-card
  администратором не входит в CB-10 и будет подключено отдельным application
  маршрутом поверх общей модели.
- Уровень проверяется через активную product-config version, а не через
  `members.level_number`.
- Статическая acceptance eligibility получает явный `ResolvedLevel` с identity
  активной config version; объект `Member` и cached level для решения
  недостаточны.
- Все изменяющие Telegram-операции используют exact update receipt и один
  commit. Экономические эффекты выполняются через публичный caller-owned UoW из
  CB-7.

## Фактическая база

- Миграция `0005` уже создаёт восемь категорий и восемь неизменяемых шаблонов.
- `CatalogService.for_creation` возвращает точную доступную версию и проверенный
  input; историческая версия читается по UUID.
- `EconomyMutationPort.prepare_batch` сначала берёт economy idempotency gates,
  затем блокирует участников в каноническом UUID-порядке и только после этого
  применяет ledger/cache effect.
- `reserve_reward` и `refund_reward` уже обеспечивают знак суммы, нулевой опыт,
  идемпотентность и запрет отрицательного доступного баланса.
- PostgreSQL 18, async SQLAlchemy, Alembic и synthetic aiogram являются
  утверждённым контуром. Production long polling остаётся за границами задачи.

## Принятые границы CB-10

- Реализуется полный member-origin цикл: один или несколько возобновляемых
  черновиков → preview →
  publish → собственный список → отмена до первого назначения.
- Принятие и создание assignment относятся к CB-11. CB-10 предоставляет
  обязательную публичную проверку eligibility, которая исключает автора, но не
  создаёт assignment.
- CB-10 разрешает отмену только состояния `published`, которое создаёт сама.
  До включения acceptance CB-11 обязана расширить этот же caller-owned UoW
  assignment-aware проверкой и гонкой accept/cancel; CB-10 не заявляет проверку
  ещё не существующих assignment rows или заполненности слотов.
- Outbox в этой задаче только долговечно фиксирует `task.published` и
  `task.cancelled`; worker доставки реализуется в задаче уведомлений.
- Полная регрессия MVP остаётся в CB-16.
