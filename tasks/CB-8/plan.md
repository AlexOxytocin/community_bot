# CB-8 — план регистрации по приглашению и профиля

## Цель

Дать приглашённому человеку законченный Telegram-сценарий: принять действующее
приглашение, возобновляемо заполнить анкету, отправить её на модерацию, после
одобрения ровно один раз получить `5` кредитов без опыта, открыть собственную
карточку и изменить её поля.

## Уровень процесса

Уровень 3 по ADR-0004: задача одновременно меняет контроль доступа,
PostgreSQL-схему, Telegram FSM и транзакцию стартового гранта. План проверяется
один раз как полный пакет; реализация и целевые проверки выполняются одним
циклом. Полная регрессия MVP остаётся в CB-16.

Новое ADR не требуется: решение остаётся внутри принятого ADR-0005 модульного
монолита и использует общий SQLAlchemy unit of work и журнал CB-7.

## Область изменений

- выдача и отзыв приглашений активным администратором;
- хранение только SHA-256 хеша высокоэнтропийного invite-токена;
- атомарное ограничение срока, адресата и числа использований приглашения;
- постоянная registration state machine в PostgreSQL;
- согласие, имя, город, часовой пояс, описание, цель, категории помощи, навыки и
  доступность;
- отправка анкеты, очередь модерации, одобрение или отклонение активным
  модератором/администратором;
- атомарная активация с единственным `starting_grant` и аудитом;
- собственная карточка и редактирование её полей;
- Telegram-команды и callback-кнопки этого сценария;
- миграция, целевые unit/integration-тесты и синтетический Telegram smoke.

## Вне области изменений

- просмотр чужих карточек до решения Q-011;
- каталог заданий, категории каталога и рекомендации;
- production deployment, webhook/outbox и полная регрессия MVP;
- автоматическая активация без решения модератора;
- хранение открытых invite-токенов, Telegram-сессий или Bot API token.

## Текущее состояние

- `/start` умеет только выбрать минимальный маршрут; приглашений, анкеты,

## Предлагаемое решение

### Данные

Миграция `0004` добавит:

- `invitations`: UUID, уникальный `code_hash`, создатель, необязательный
  `intended_telegram_user_id`, `max_uses`, `uses_count`, срок, отзыв и даты;
- `invitation_redemptions`: уникальная пара приглашение/участник и уникальный
  участник, чтобы одно создание аккаунта не расходовало несколько кодов;
- `registration_applications`: один текущий статус `draft/submitted/approved/
  rejected` на участника, даты решения и модераторский комментарий;
- `conversation_states`: `member_id`, `flow_type`, `current_step`, JSON payload,
  срок и дата изменения;
- в `members` — JSON-массивы кодов категорий помощи и тегов навыков. Они являются
  снимком карточки до появления управляемого каталога CB-9; CB-9 сможет
  нормализовать их без потери пользовательского текста.

Открытый токен создаётся криптографически случайным, показывается администратору
только в результате создания и никогда не пишется в БД, аудит или логи. Для
идемпотентного повтора того же Telegram update токен детерминированно выводится
из отдельного runtime secret и `update_id`; в БД остаётся только SHA-256.

### Регистрация

`/start <token>` в одной транзакции сначала сериализует Telegram update, затем
получает отдельный advisory gate по полному Telegram user ID, повторно читает
member и только после этого блокирует строку приглашения. Gate идентичности
сериализует и разные update одного пользователя: проверка срока/отзыва/
адресата/лимита создаёт ровно одного `pending` участника, redemption, draft
application и состояние `consent`.
Повторный `/start` находит участника по неизменному Telegram user ID, обновляет
только текущий username и возвращает сохранённый шаг, статус модерации либо меню.

Шаги имеют закрытый порядок:

```text
consent → display_name → city → timezone → short_bio → current_goal
→ help_categories → skill_tags → availability → preview → submitted
```

Каждая изменяющая команда анкеты содержит `expected_step`, который transport
получает при показе вопроса. Транзакция берёт update gate, проверяет exact
receipt, затем identity gate, заново читает состояние и применяет ответ только
при совпадении шага. Повтор update возвращает сохранённый outcome, а другой
запоздавший ответ получает `stale_step` и не меняет payload. Новое состояние
фиксируется до ответа Bot API. Валидация длины, timezone через `zoneinfo`,
непустых списков и согласия находится в доменном коде. `/cancel` не удаляет
черновик: следующий `/start` продолжает его. Тот же протокол используется для
submit, reject-resume и редактирования профиля.

### Модерация и грант

`/registrations` доступна только активному moderator/administrator. Решение
передаёт UUID заявки в callback и повторно проверяет право и принадлежность на
сервере.

Для безопасной композиции расширяется публичный economy port минимальным
двухфазным примитивом `prepare_batch(commands, additional_member_ids)`. Он
получает все economy idempotency gates, выполняет exact reads и блокирует
command members вместе с дополнительными actor/target UUID в каноническом
порядке. Возвращённый `PreparedEconomyBatch` содержит неизменяемые member
snapshots и метод `apply()`. До `apply()` журнал и кэши не меняются; внешний UoW
остаётся единственным владельцем commit. Обычный `apply_batch()` внутри
использует тот же prepare/apply путь, поэтому второй economy API не появляется.

Одобрение выполняется одной транзакцией:

1. update gate и exact receipt read;
2. разрешение actor/target IDs без решения о доступе;
3. `prepare_batch(starting_grant, actor_id)` получает economy gate и общий
   канонический lock actor/target rows без записи гранта;
4. по возвращённым locked snapshots проверяются роль, `submitted` и `pending`;
5. `PreparedEconomyBatch.apply()` добавляет единственный грант `+5/+0`, затем
   сохраняются `status=active`, `approved_at`, решение
   заявки, audit и receipt;
6. один commit.

Повтор того же или другого одобрения возвращает сохранённый `approved` без
второго гранта. Отклонение оставляет member `pending`, помечает заявку
`rejected`, хранит краткую причину и позволяет пользователю снова открыть анкету
на редактирование и повторно отправить её.

### Профиль и Telegram UI

`/profile` разрешена владельцу активного профиля и показывает поля карточки,
баланс, опыт и уровень из активной конфигурации. Inline-кнопки выбирают поле;
следующее сообщение валидируется и атомарно обновляет только собственный профиль.
Q-011 не затрагивается: маршрута чтения чужой карточки задача не добавляет.

## Шаги реализации

1. Добавить доменные типы/валидацию регистрации и профиля.
2. Добавить прикладной service и расширить общий unit of work безопасной
   композицией с economy.
3. Добавить SQLAlchemy-модели и обратимую миграцию `0004`.
4. Реализовать Telegram router и представления.
5. Добавить целевые тесты и обновить data model/flows/interface при фактических
   уточнениях.
6. Выполнить целевые проверки, отчёт и одну финальную независимую проверку.

## Риски и меры снижения

- Гонка последнего использования invite: row lock и DB CHECK.
- Двойной grant: стабильный business key, unique index и одна транзакция.
- Дедлок actor/target/economy: `prepare_batch` всегда получает idempotency gates
  до канонически отсортированных member locks; authorization выполняется после
  lock, но до первого ledger effect.
- Параллельные разные updates одного пользователя: update gate → identity gate
  → exact state/expected step; запоздавшая команда остаётся без эффекта.
- Утечка invite: только hash в persistence/audit/logs, токен маскируется в
  сообщениях об ошибках.
- Потеря анкеты: каждый переход хранится в PostgreSQL до Telegram-ответа.
- Раздувание процесса: без полной регрессии и без ревью промежуточных слайсов.

## Проверки

- unit: переходы FSM, валидация, права и представления;
- PostgreSQL integration: приглашения, restart/resume, username, конкуренция,
  approval/reject/resubmit, грант и rollback;
- synthetic aiogram smoke полного сценария без сетевого Bot API;
- миграция `0003 → 0004 → 0003 → 0004` на тестовой БД;
- Ruff, ty и проверка diff только после готовности полного кода.
