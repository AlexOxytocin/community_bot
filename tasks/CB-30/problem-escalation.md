# CB-30 — консолидированная эскалация плана

## Причина

Два последовательных plan-review завершились `changes_requested`. По принятому
правилу дальнейшие узкие циклы остановлены, оба verdict сохранены в
`reviews/plan/`, а исправления сведены в один контрольный пакет.

## Полный набор причин

| Код | Причина | Консолидированное решение | Проверка |
|---|---|---|---|
| E-001 | нет independent community reviewer | поля creator/reviewer, запреты конфликтов, `reviewer_required`, replacement | сценарии 16–17, 25 |
| E-002 | text drafts конкурируют | один owner в `conversation_states`, atomic claim/switch/cancel/restart | сценарии 21–22 |
| E-003 | fraud/raw karma скрыты | безопасные admin cards, permission/privacy/audit, exact revision | сценарии 12–13 |
| E-004 | request и resolve appeal смешаны | party request и independent admin resolution разделены | сценарий 9 |

## Контрольный барьер

Следующий review является не новым поисковым циклом, а финальным контролем всего
набора E-001–E-004 и отсутствия регрессии пяти Jira AC. Реализация начинается
только при точном `Status: approved`. Если контроль снова не пройдёт, работа
останавливается для решения владельца, без автоматической нарезки новых циклов.

## Эскалация финальной проверки

Два последовательных final-review сохранены в `reviews/final/`. Консолидированный
пакет исправления состоит из трёх связанных частей:

1. Миграция сохраняет community creator/reviewer во внутреннем migration marker
   при downgrade и восстанавливает их с удалением marker при re-upgrade; прямой
   тест сохраняет также assignment и точные ledger UUID.
2. Production Dispatcher доказывает visible partial и no-show карточки, а также
   существующие full/reject ветки.
3. `community-worker` реально композирует bounded assignment deadline worker;
   тот выбирает due tasks и вызывает канонический транзакционный finalizer до
   materialization/notification tick.

Следующий final-review является единственным эскалационным контролем этого пакета.
Если он снова не одобрен, автоматическая работа останавливается для решения владельца.

## Решение владельца по M-003

Дата: 2026-08-12.

Владелец подтвердил минимальный вариант без расширения архитектуры: production source
выбирает только просроченные задачи, в которых существует assignment со статусом
`accepted`. Старые `settling`-задачи с `submitted`, `disputed`,
`rejected_pending_dispute` или `reviewer_required` не занимают bounded-пачку.

Решение проверяется прямым PostgreSQL-сценарием с пачкой размера один: более старое
недействующее задание остаётся без изменений, а следующее принятое задание попадает в
воркер и завершается как `no_show`. После этого разрешён один контрольный final-review
подтверждённого исправления; новый цикл поиска архитектурных вариантов не открывается.
