# CB-30 — план непрерывных Telegram-цепочек MVP

## Цель

Убрать из обычной работы бота внутренние UUID, revision, JSON и скрытые
slash-команды. После каждого действия следующий допустимый шаг должен приходить
в ответе Bot API как понятная кнопка либо запрос обычного текста. Существующие
прикладные транзакции, права, идемпотентность и бухгалтерская книга остаются
единственным местом применения бизнес-эффектов.

## Пользовательский контракт

1. `Мои задания` показывает две понятные части: собственные опубликованные
   задания и принятые выполнения. В карточке показываются название и русский
   статус, а допустимые действия выводятся inline-кнопками.
2. После `Взять` исполнитель сразу получает кнопки `Отправить результат` и
   `Отказаться`. После перезапуска те же действия восстанавливаются через
   `Мои задания`.
3. Результат вводится обычным сообщением. Для единственной принятой в MVP
   схемы `standard_result` текст преобразуется в `summary`, один `finding` и
   пустой список `evidence`, затем показывается предпросмотр с подтверждением.
   UUID и revision хранятся в существующем PostgreSQL-черновике и callback.
4. Автор видит submitted-выполнения своего задания и кнопки `Принять полностью`,
   `Принять частично`, `Отклонить`. Исполнитель отклонённого результата получает
   кнопку `Открыть спор`, вводит приватный комментарий и подтверждает действие.
5. Очередь модерации показывает карточки случаев и допустимые решения. Сторона
   resolved-случая видит `Подать апелляцию`; moderator/administrator получает
   только разрешённые ролью действия. Санкции и interaction alerts открываются
   из административного меню и применяются готовыми ограниченными вариантами,
   без ручных идентификаторов.
6. Оплаченные назначения доступны active administrator отдельными безопасными
   карточками `Проверить выплату`; `Открыть расследование` вызывает существующий
   post-payment fraud service. Каталог участников для администратора дополнительно
   даёт `Проверить карму`: raw author/comment/history выводятся только в личный
   ответ прошедшему `karma_review` administrator, чтение аудируется, а
   exclude/restore применяется кнопкой к точным vote id/revision. Member и
   moderator не получают ни raw-данные, ни callbacks.
7. Каталог участников показывает безопасные карточки с `Открыть профиль` и
   `Оценить`. Значение выбирается кнопкой, комментарий вводится обычным текстом,
   подтверждение берётся из ответа бота.
8. Создание member и community заданий использует один текущий черновик:
   описание и материалы вводятся текстом, срок/формат/число мест выбираются
   кнопками, публикация выполняется из предпросмотра. Community-вариант доступен
   только active administrator, публикуется без личного автора и резерва, а
   выплата остаётся `community_task_reward`.
   Перед публикацией community-карточки creator выбирает из выданного ботом
   списка другого active administrator. В опубликованном снимке сохраняются
   `created_by_admin_id` и `reviewer_admin_id`; creator и любой performer не могут
   быть reviewer. Если reviewer стал неактивным или конфликтным, settlement
   переходит в `reviewer_required`, а другой active administrator назначается
   видимой кнопкой без изменения исходного review deadline при добровольной
   замене и с новым 72-часовым окном при вынужденной замене.
9. `/cancel` отменяет только текущий текстовый диалог; повтор открытия карточки
   восстанавливает допустимые действия. Exact replay одного update возвращает
   сохранённый исход и не создаёт второй receipt, ledger, audit или outbox.

## Реализация

1. Добавить небольшие read-модели assignment/review/moderation/alert для
   формирования карточек. Запросы авторизуются в application service; transport
   не читает БД напрямую.
2. Сделать существующую строку `conversation_states` единственным durable
   владельцем свободного текста. Начало task/result/dispute/karma/profile-edit
   под identity gate атомарно записывает `flow_type`, reference и revision;
   сохранённые предметные drafts остаются данными, но не конкурируют за input.
   Production conversation router сначала читает ровно одного владельца и
   вызывает только его handler. Switch сохраняет предметный draft, но меняет
   владельца; `/cancel` удаляет/закрывает только draft указанного владельца и
   очищает owner. Registration/profile-edit нельзя молча вытеснить: сначала
   требуется их явная отмена.
3. Расширить `task_creation_drafts` полями `origin` и `reviewer_admin_id`, а
   `tasks` — каноническими `created_by_admin_id` и `reviewer_admin_id` через
   Alembic. Для legacy drafts значение `member`; legacy tasks сохраняются без
   новых ссылок. Community publish повторно блокирует/проверяет creator и
   reviewer, не создаёт reserve-команду, сохраняет `creator_id = NULL` и обе
   административные ссылки. Видимая replacement-команда повторно проверяет
   active role, creator/performer conflict и сериализуется task gate.
4. Собрать все новые кнопки в существующих routers и передать уже созданные
   экземпляры сервисов в navigation/conversation. Прикладные mutation methods не
   дублируются в transport.
5. Обновить справку и пользовательские тексты. В ответах нет UUID, revision,
   JSON, приватных комментариев, evidence и технических статусов.

## Права и атомарность

- performer может менять только своё назначение и спорить только в допустимом
  окне;
- member-author проверяет только назначения своих member-задач;
- community assignment проверяет active administrator;
- community review выполняет только сохранённый независимый reviewer; creator,
  performer, другой administrator и stale reviewer callback не получают эффект;
- moderator разрешает спор и применяет только разрешённые ему санкции;
- request appeal разрешён только active case party — performer либо creator — в
  `[resolved_at, resolved_at + 7d)`; appealed case решает другой active
  administrator без конфликта;
- ban, fraud reversal, денежный penalty, raw karma и interaction alert остаются
  administrator-only согласно D-023;
- любой callback является лишь transport-командой: окончательное право заново
  проверяет application/domain слой внутри того же PostgreSQL UoW;
- raw karma read всегда проходит `karma_review`, создаёт audit даже без mutation,
  а moderation callback повторно сверяет точные vote id/revision;
- существующий порядок `update gate -> identity/task/case gate -> rows -> effect
  -> receipt -> commit` не меняется.

## Границы

- не создаётся отдельная веб-админка, универсальный workflow engine или новый
  transport framework;
- не меняются формулы выплат, окон спора/апелляции, санкций, karma и alerts;
- Telegram callback может содержать технический идентификатор, но пользователь
  его не вводит и E2E получает callback только из предыдущего ответа Bot API;
- полный продуктовый regression остаётся в CB-29 после слияния всех Bugs. В
  CB-30 выполняется широкий PostgreSQL/production Dispatcher E2E только
  затронутых цепочек.
