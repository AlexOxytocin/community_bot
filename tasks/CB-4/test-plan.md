# CB-4 — план проверки продуктовых решений

## Предусловие

Проверки выполняются после явного подтверждения владельца и синхронизации документов. Это документационная задача: Python-код, миграции и Telegram Bot API не запускаются и не изменяются.

## Сценарии

| № | Проверка | Ожидаемый результат |
|---:|---|---|
| 1 | Найти заголовки `Q-002`, `Q-003`, `Q-004`, `Q-007`, `Q-008`, `Q-009`, `Q-010`, `Q-012` в разделе открытых вопросов | Ни одного; вместо них есть датированные принятые решения с причиной и отклонёнными вариантами |
| 2 | Проверить seed и активацию уровней | Ровно 10 уровней; пороги `0, 10, 25, 50, 100, 180, 300, 450, 650, 1000`; названия совпадают; одна active scale применяется ко всем текущим участникам; stale cache во время backfill не влияет на profile, `minimum_level`, acceptance, leaderboard или notification decision и не меняет ledger |
| 3 | Проверить все границы уровня | Для каждого порога `10/25/50/100/180/300/450/650/1000` значения `threshold-1` и `threshold` дают соответственно предыдущий и новый уровень; опыт выше 1 000 остаётся уровнем 10; параллельное чтение при переключении шкалы не наблюдает смешанный набор порогов |
| 4 | Проверить стартовый грант | Ровно 5 кредитов после первого одобрения; 0 опыта; два конкурентных approval/update с разными transport update и одним участником создают одну `starting_grant`; повтор после restart возвращает сохранённый результат без второго гранта |
| 5 | Проверить варианты истечения и гонку | Для многоместного task независимо разрешаются unfilled/no-submission/submitted slots; агрегат остаётся `settling`, затем становится `expired`, `partially_completed` или `completed`; concurrent first submission и expiration сериализуются в один исход с одним refund либо сохранённым review reserve, без `no_show` и refund одновременно с принятым result |
| 6 | Проверить позднюю коррекцию `no_show` | Модераторское подтверждение вины автора/системы добавляет корректирующее событие и меняет reliability denominator, не удаляя assignment/audit и не создавая скрытую выплату |
| 7 | Проверить точные границы окна автора | В `review_deadline_at - 1 микросекунда` ручное решение/спор допустимы; при `now = review_deadline_at` допустим только autoconfirm; concurrent dispute/autoconfirm даёт один сериализованный исход и один ledger effect |
| 8 | Проверить версии и напоминания | Первая result version за 1 микросекунду до task deadline допустима, на границе запрещена; append-only дополнение в нерешённом review допустимо и не сдвигает 72 часа; после решения/спора обычная версия запрещена; решения до 24/48 часов подавляют напоминания; повтор worker не отправляет дубликат |
| 9 | Проверить partial одного места | Награда 1: partial запрещён; награды 2/3/4: исполнителю 1/2/2; paid+refund равны reserve slice одного assignment, другие места и их резервы не меняются; concurrent duplicate создаёт один эффект |
| 10 | Проверить состав антифарм-лимита | Active, paid, performer refusal и `no_show` assignment считаются один раз; creator/system-fault exclusion не считается; active старше 30 суток считается до завершения |
| 11 | Проверить временную границу антифарма | Предыдущий terminal assignment с `accepted_at = T-30 суток` уже не считается, с `accepted_at > T-30 суток` считается; направление пары и версия шаблона не меняют ключ |
| 12 | Проверить конкурентность и версию антифарма | Две параллельные попытки занять последнее разрешённое место дают один success; новая policy/template version не сбрасывает историю, snapshot решения сохраняется |
| 13 | Проверить общественные действия и административную границу | Свободного production `community_bonus` нет; вознаграждаемое действие возможно только через фиксированный шаблон; member/moderator получают отказ на `admin_adjustment`; active administrator с отдельным правом, причиной и новым idempotency key создаёт одну операцию и audit, повтор ключа не начисляет снова |
| 14 | Сопоставить журнал решений с PRD, доменными правилами, flows, каталогом, интерфейсом, data model, moderation, implementation plan и test plan | Нет старых гипотез `TBD`, противоположных формул или неоговорённых значений по умолчанию |
| 15 | Проверить миграционные последствия | Для каждого Q указано, какая будущая schema/seed/index/transaction работа потребуется или почему миграция не нужна |
| 16 | Проверить будущие автоматические тесты | Для каждого Q есть граничный и идемпотентный сценарий; для шкалы, дедлайна, автоподтверждения, partial и антифарма есть concurrency-сценарий |
| 17 | Проверить локальные Markdown-ссылки изменённых файлов | Каждая относительная ссылка разрешается в существующий файл |
| 18 | Выполнить `git diff --check origin/main...HEAD` и `git diff --cached --check` перед коммитом | Обе команды завершаются с кодом 0 |
| 19 | Проверить язык и секреты | Смысловой текст на русском; нет токенов, учётных данных, приватных идентификаторов и секретоподобных значений |

## Команды контроля

```powershell
rg -n "Q-(002|003|004|007|008|009|010|012)|TBD|50%|30 дней|стартов" docs/mvp
rg -n "0, 10, 25, 50, 100, 180, 300, 450, 650|72|24|48|ceil|community_bonus" docs/mvp tasks/CB-4
git diff --check origin/main...HEAD
git diff --cached --check
```

Локальные Markdown-ссылки проверяются скриптом чтения всех изменённых `.md`: внешние URL пропускаются, относительные пути разрешаются от каталога исходного файла, отсутствующий target завершает проверку ошибкой.

## Барьер завершения

Нельзя отмечать сценарий пройденным только по наличию числа в одном файле. Доказательством является одновременное совпадение журнала решений, всех связанных документов, матрицы миграционных последствий и будущих тестов.
