# CB-6 — контекст и источники плана

`community_bot.plan_source_context.v1`

## Jira

- Задача: `CB-6` — «Реализовать фундамент участников, ролей, аудита и защиты от повторных updates».
- Родитель: эпик `CB-2` — «Реализовать и подготовить к пилоту Community Bot MVP», статус `В работе`.
- Статус и приоритет: `К выполнению`, `Medium`.
- Комментарий: зависимость бэклога подтверждает, что `CB-3` блокирует `CB-6`.
- Входящая блокирующая связь: `CB-3`, статус `Готово`; фактического открытого блокера нет.
- Исходящие связи: `CB-6` блокирует `CB-7` и `CB-9`, обе задачи пока `К выполнению`.
- Доступные переходы перед планированием: `К выполнению`, `В работе`, `На проверке`, `Готово`. Отдельного эквивалента `Планирование` нет, поэтому статус не изменён.

### Критерии приёмки Jira

1. Новый и существующий Telegram user маршрутизируются детерминированно.
2. Повтор одного update не создаёт второе доменное действие.
3. Запрещённая роль или статус получает отказ после серверной проверки.
4. Значимое административное действие оставляет audit event.
5. Перезапуск процесса не теряет сохранённое состояние.
6. Unit, integration и migration tests проходят.

- `docs/PROJECT_RULES_AND_GUARDRAILS_RU.md`: Jira-first, одна задача — одна ветка, детерминированные проверки, идемпотентность и запрет секретов.
- `docs/AGENT_WORKFLOW.md`, `docs/JIRA_WORKFLOW.md`, `agents/workflow.yaml`: жизненный цикл задачи, независимые ревью и точные переходы Jira.
- `docs/adr/0004-risk-tiered-development-workflow.md`: CB-6 относится к уровню 3, потому что затрагивает интеграцию Telegram/PostgreSQL, авторизацию, аудит и идемпотентность.
- `docs/adr/0005-mvp-technology-stack.md`: Python 3.13, модульный монолит, aiogram 3.x, PostgreSQL 18, SQLAlchemy 2 async, Alembic; сессии нельзя делить между конкурентными задачами.
- `docs/adr/0006-telegram-update-transaction-boundary.md`: сквозное решение CB-6; exactly-once ограничено эффектом PostgreSQL, а Bot API вызывается только после commit. Владелец явно принял ADR 2026-08-10 до реализации.
- `docs/ARCHITECTURE.md`: Telegram transport не содержит бизнес-правил; домен не зависит от aiogram и SQLAlchemy; повтор update не создаёт повторное необратимое действие.
- `docs/mvp/01_PRODUCT_REQUIREMENTS.md`: роли, статусы аккаунта, серверная авторизация, UTC, аудит администратора и восстановление после перезапуска.
- `docs/mvp/02_DOMAIN_RULES.md`: атомарность и идемпотентность доменных изменений; экономика остаётся вне CB-6.
- `docs/mvp/06_DATA_MODEL.md`: концептуальные `members` и `audit_events`; для требования дедупликации потребуется отдельная таблица обработанных Telegram updates.
- `docs/mvp/07_SECURITY_AND_PRIVACY.md`: Telegram user ID — постоянный внешний идентификатор; callback и UI не являются авторизацией; роль, статус и владение перепроверяются на сервере.
- `docs/mvp/09_IMPLEMENTATION_PLAN.md`: этап 1 включает модель участника, роли, статусы, авторизацию, аудит, дедупликацию и базовое меню.
- `docs/mvp/10_TEST_PLAN.md`: повторный `/start`, поддельный callback, запрещённые статусы, повторная доставка после timeout и конкурентные запросы.
- `docs/mvp/11_DECISIONS_AND_OPEN_QUESTIONS.md`: D-009 разделяет роль и уровень; открытые продуктовые вопросы не блокируют фундамент CB-6 и не будут молча решаться в коде.

## Ограничения

- Не реализовывать приглашения, регистрацию, заполнение профиля, стартовые кредиты, задания, каталог, экономику, карму, споры и outbox-уведомления.
- Не выполнять реальные Telegram-операции и не требовать токен для тестов.
- Не хранить Telegram token, приватные чаты или персональные фикстуры в репозитории.
- Не использовать Jira key в исполняемых именах.
- Все timestamps сохранять как timezone-aware UTC.
- Дедупликация должна жить в PostgreSQL и быть атомарной с доменным действием; память процесса и Telegram UI не считаются защитой. Гарантия не распространяется на внешнюю отправку Bot API.
- Bot API запрещён внутри открытой транзакции; безопасный ответ отправляется после commit и может быть повторён или потерян до появления outbox для критических сообщений.
- Полный локальный integration-прогон обязан исполняться без `skip`: при отсутствии `DATABASE_URL` fixture автоматически поднимает `postgres:18` через Testcontainers; при недоступном Docker тесты завершаются ошибкой.
- Реализация должна оставаться внутри принятых ADR-0005 и ADR-0006.

## Открытые вопросы

- Блокирующих вопросов нет: план независимо одобрен, ADR-0006 явно принят владельцем 2026-08-10.
- Точные разрешения `restricted` будут развиваться в задачах модерации; в CB-6 безопасное правило по умолчанию запрещает обычные действия всем статусам, кроме `active`.
- Открытые `Q-002`–`Q-012` не затрагиваются: CB-6 не создаёт production seed экономики, уровней, кармы или профилей.
