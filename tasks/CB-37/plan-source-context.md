# CB-37 - контекст источников плана

## Подтверждённое текущее состояние

- `TaskService.cancel` отменяет только `published` task без любой истории
  назначений и возвращает полный резерв.
- `AssignmentService.cancel` позволяет исполнителю отменить собственное
  назначение только в состоянии `accepted`.
- `list_owned_tasks` возвращает task snapshot без исполнителей, хотя
  `AssignmentCard` уже содержит отображаемое имя исполнителя.
- Telegram «Мои задания» сейчас отправляет полную карточку и отдельную кнопку
  «Отменить».
- Notification worker доставляет durable-события через outbox и PostgreSQL
  notification queue, но интерактивные уведомления пока не используют payload
  для inline keyboard.
- Domain rules запрещают отмену после отправки результата; это правило
  сохраняется.

## Решение владельца от 14 августа 2026 года

Владелец явно запросил компактный заголовочный список, раскрытие полной карточки
по `+`, видимость занятости и имени исполнителя, немедленную отмену свободного
задания и согласование отмены занятого задания с исполнителем.

## Интерпретация неоднозначностей

- «Уже начал» является заявлением исполнителя, а не автоматически вычисляемым
  состоянием: после принятия и до submit система не может достоверно наблюдать
  начало фактической работы.
- Для нескольких слотов требуется согласие всех активных исполнителей; иначе
  отмена нарушила бы право не ответившего участника.
- Повторный запрос после отказа запрещён как защита от давления.
- Pending-запрос временно блокирует новые accept, чтобы состав согласующихся
  исполнителей не менялся после создания пакета.
- Самостоятельная отмена исполнителя не считается ответом «уже начал»: пакет
  устаревает, после чего автор может повторить отмену по актуальному составу.
- Согласованная отмена относится к причине автора и не ухудшает reliability
  исполнителя.
- В компактном виде кроме заголовка остаются только сведения, которые владелец
  потребовал видеть сразу: занятость и отображаемые имена.

## Затрагиваемые границы

- domain: статусы и DTO запроса отмены;
- application: request/respond orchestration и owned-task projection;
- infrastructure: Alembic, SQLAlchemy models, repositories, outbox materializer;
- transport: compact/expanded messages и callbacks;
- worker: payload-driven inline keyboard для allowlisted notification type;
- docs/tests: решение, flows, interface, output-driven и PostgreSQL regression.

Структурная форма приложения и технологический стек не меняются, поэтому новый
ADR не требуется.
