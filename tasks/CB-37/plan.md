# CB-37 - план реализации

## Цель

Сделать список собственных заданий компактным и дать автору безопасный сценарий
отмены как свободного, так и занятого задания без принудительного прекращения
уже начатой работы.

## Продуктовый контракт

1. Свёрнутая карточка показывает название, состояние занятости и имена активных
   исполнителей, но не показывает полное описание, материалы, срок и формат.
2. Кнопка `+` заменяет текст того же Telegram-сообщения полной карточкой;
   кнопка `−` возвращает компактный вид.
3. Для свободного задания автор проходит подтверждение, после чего задание
   отменяется сразу и резерв возвращается ровно один раз.
4. Для задания с назначениями `accepted` подтверждение автора создаёт один
   durable-запрос каждому активному исполнителю.
5. Исполнитель выбирает «Согласен отменить» или «Уже начал(а), не отменять».
6. Только согласие всех активных исполнителей атомарно отменяет назначения и
   задание и возвращает резерв. Один отказ сохраняет задание.
7. После отправки результата, проверки, спора или терминального состояния
   запрос недоступен.
8. Повторный запрос после отказа не создаётся, чтобы автор не мог давить на
   исполнителя повторными уведомлениями.
9. Пока запрос ожидает ответы, новые исполнители не могут занять свободный слот.

## Реализация

1. Добавить transport-neutral DTO компактной авторской карточки с активными
   исполнителями и состоянием запроса отмены.
2. Расширить PostgreSQL-проекцию «Мои задания» данными активных назначений.
3. Добавить таблицы пакета запроса отмены и ответов исполнителей с конечными
   автоматами, внешними ключами, уникальностью и индексами.
4. Добавить прикладные команды запроса и ответа с блокировкой task aggregate,
   проверкой владельца, статусов, идемпотентностью update и аудитом.
5. В `accept` под существующим task gate запрещать новое назначение, пока у
   задачи есть pending-пакет отмены.
6. При свободном задании разрешить отмену даже при отменённой исторической
   записи назначения, если активных назначений и результатов нет.
7. В транзакции авторского запроса создавать отдельный outbox-event на каждую
   pending response. Materializer переносит allowlisted response ID и название
   задания в notification payload, а sender строит стабильную inline keyboard
   из persisted ID. Retry использует тот же callback.
8. Добавить callback-маршруты раскрытия, сворачивания, подтверждения запроса и
   ответа исполнителя. Все callback data кодируют UUID компактно и остаются
   private-only.
9. Обновить интерфейс, пользовательские потоки, доменные правила и журнал
   решений `D-027`.

## Конечные автоматы

Пакет запроса:

- `pending -> completed`, когда все исходные active assignments дали согласие;
- `pending -> declined`, когда хотя бы один исполнитель выбрал «Уже начал(а)»;
- `pending -> obsolete`, если раньше ответа отправлен результат, исполнитель
  самостоятельно отменил назначение либо наступил дедлайн;
- `declined`, `completed`, `obsolete` терминальны.

Ответ исполнителя:

- `pending -> accepted|declined` только владельцем соответствующего assignment;
- все оставшиеся `pending -> obsolete` при `declined` или `obsolete` пакета;
- `accepted`, `declined`, `obsolete` терминальны.

При самостоятельной отмене assignment pending-пакет становится `obsolete`, и
автор может повторить действие: если активных назначений больше нет, task
отменяется сразу. При submit или дедлайне пакет становится `obsolete`, но отмена
task остаётся запрещённой текущими доменными правилами.

## Транзакционные гарантии

- один Telegram update даёт один receipt и один эффект;
- на одну задачу существует не более одного `pending` пакета отмены;
- один assignment имеет ровно один ответ в пакете;
- accept, submit, самостоятельная отмена, дедлайн и ответ на отмену
  сериализуются общей блокировкой task aggregate;
- возврат использует существующий стабильный idempotency key задачи;
- outbox и изменение доменного состояния записываются одной транзакцией;
- чужой callback не раскрывает авторскую карточку и не меняет запрос.
- согласованная отмена пишет append-only reliability outcome
  `cancelled_creator`, который исключается из знаменателя надёжности; путь
  `cancelled_performer` для самостоятельной отмены не переиспользуется.
- notification с кнопками отправляется только пока пакет и response `pending`,
  assignment `accepted`, а task `published`; иначе claim помечается obsolete.

## Вне области

- принудительная отмена автором после отказа исполнителя;
- переговоры и свободный текст внутри запроса;
- штрафы или изменение кармы за согласованную отмену;
- изменение правил отмены community-task: такие карточки тоже сворачиваются и
  показывают занятость, но не получают авторскую кнопку отмены;
- автоматическое определение фактического начала работы.

## Риски

- гонка между отправкой результата и ответом на отмену закрывается task gate;
- частичное согласие многоместного задания не меняет назначения до единогласия;
- недоставленное уведомление остаётся в retryable notification queue;
- старые Telegram-кнопки продолжают проходить текущую проверку владельца и
  состояния через application service.
