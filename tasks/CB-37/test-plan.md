# CB-37 - план проверки

## Автоматические сценарии

1. Свёрнутая карточка содержит название и «Свободно», но не полное описание,
   материалы, срок или формат.
2. Занятая карточка показывает имя каждого активного исполнителя и заполнение
   слотов; отменённая историческая assignment не отображается как активная.
3. Callback `+` из фактического Bot API ответа редактирует то же сообщение в
   полную карточку; `−` возвращает компактный текст.
4. Чужой и групповой callback отклоняются без чтения приватной карточки.
5. Свободное задание после двух шагов становится `cancelled`, получает один
   refund и не получает второй при replay.
6. Занятое задание создаёт один пакет и по одной pending response на каждого
   `accepted` исполнителя; replay и повторный запрос не создают дубликаты.
7. Worker материализует каждому исполнителю адресное уведомление с кнопками,
   полученными из persisted response ID.
8. Частичное согласие не отменяет ни task, ни assignments и не возвращает
   резерв.
9. Последнее согласие атомарно отменяет все `accepted` assignments и task,
   возвращает резерв один раз и уведомляет участников.
10. Отказ помечает пакет `declined`, сохраняет task и assignments и уведомляет
    автора; повторный запрос запрещён.
11. Submit, возникший раньше ответа, блокирует отмену; ответ, выигравший гонку,
    блокирует последующий submit.
12. Две синхронизированные PostgreSQL-транзакции проверяют оба порядка
    завершения последнего согласия и `confirm_submission_draft`, включая
    многоместный пакет после частичного согласия. Проверяются task/assignment,
    receipt, refund, audit, reliability и outbox.
13. Новый accept во время pending-пакета отклоняется; самостоятельная отмена
    assignment и deadline переводят пакет в `obsolete` и снимают блокировку.
14. Согласованная отмена создаёт `cancelled_creator`, не увеличивает
    `accepted_assignments` в reliability denominator и не создаёт
    `cancelled_performer`.
15. Фактический Telegram sender использует persisted payload-кнопки; retry после
    `TelegramRetryAfter` и network error сохраняет callback, delivery
    дедуплицируется, а закрытый пакет делает notification obsolete.
16. Community-task сворачивается и показывает исполнителей, но не получает
    кнопку авторской отмены.
17. Callback data не превышают 64 bytes; неизвестный, устаревший и чужой ID
    дают понятный отказ.
18. Миграция проходит на пустой и существующей схеме, downgrade удаляет только
    новые объекты.

## Production-проверка

После merge и deploy через живую пользовательскую Telegram-сессию:

1. открыть «Мои задания» и проверить компактный вид существующих карточек;
2. раскрыть и свернуть одну карточку теми callback-кнопками, которые реально
   прислал production bot;
3. создать временное свободное задание, отменить его и сверить единственный
   возврат и отсутствие активного test marker;
4. создать временное задание, принять его второй канонически доступной живой
   пользовательской сессией, отправить авторский запрос и ответить исполнителем;
5. проверить оба исхода на двух временных заданиях: согласие и «Уже начал(а)»;
6. проверить health bot/worker/PostgreSQL и отсутствие failed outbox events.

Если отдельная разрешённая пользовательская Telegram-сессия отсутствует, пункты
4-5 считаются блокировкой завершения CB-37. Проверка БД, fake Bot API или прямой
вызов application service не заменяет живой занятый сценарий.
