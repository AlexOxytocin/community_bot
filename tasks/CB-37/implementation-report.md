# CB-37 - отчёт о реализации

## Статус

Локальная реализация и автоматическая проверка завершены. Production deploy и
проверка через живую Telegram-сессию ещё не выполнялись, поэтому задача не
считается готовой к закрытию.

## Критерии приёмки

1. **Свёрнутая карточка — выполнено.** «Мои задания» показывает заголовок,
   занятость и имена активных исполнителей без описания и материалов.
   Доказательство: output-driven сценарий
   `test_task_details_are_visible_in_preview_catalog_and_acceptance`.
2. **Раскрытие в том же сообщении — выполнено.** Callback `task:view:open:*`
   вызывает `edit_text`, `task:view:close:*` возвращает исходный текст;
   callback не превышает 64 байта.
3. **Свободная отмена — выполнено.** После подтверждения task становится
   `cancelled`, резерв возвращается с прежним идемпотентным ключом.
4. **Запрос занятому исполнителю — выполнено.** Миграция `0017` добавляет
   durable request и отдельные response; outbox создаётся в той же транзакции.
5. **Отказ исполнителя — выполнено.** Пакет становится `declined`, task и
   assignment остаются активными, повторный запрос запрещён.
6. **Единогласная отмена — выполнено.** Последний ответ атомарно отменяет task и
   все `accepted` assignments, возвращает резерв один раз и пишет
   `cancelled_creator` с автором задания как actor, но не
   `cancelled_performer`.
7. **Начатая работа защищена — выполнено.** Submit и deadline переводят pending
   пакет в `obsolete`; устаревшая кнопка сообщает точную причину без изменения
   задания.
8. **Новые принятия во время запроса — выполнено.** `accept_with_task` проверяет
   pending-пакет под общей PostgreSQL task gate.
9. **Community-task — выполнено.** Карточка компактна и показывает занятость,
   но авторская кнопка отмены отсутствует.
10. **Уведомления — выполнено.** Materializer переносит только allowlisted title,
    task ID и response ID; sender строит стабильные кнопки из persisted ID;
    закрытый пакет и прошедший deadline помечают delivery как
    `notification_obsolete`.

## Исправления после final review

- запрос и ответ на отмену теперь проверяют deadline под общей task gate;
- `cancelled_creator` атрибутируется автору, а не исполнителю;
- если исполнитель освободил слот между вопросом и подтверждением, автор видит
  сообщение о немедленной отмене и возврате, а не ложное «запрос отправлен»;
- ответы на просроченные, чужие и закрытые callback получили отдельные понятные
  сообщения;
- receipt сохраняет `request_id` для partial, declined, obsolete и final replay;
- output-driven тест нажимает callback из реального
  `PostgresNotificationQueue -> NotificationWorker -> TelegramNotificationSender`;
- добавлены оба порядка гонки последнего согласия с
  `confirm_submission_draft`, post-deadline response и self-cancel.
- после второго review deadline guard добавлен и в `TaskService.cancel()`,
  включая реальный callback свободной отмены;
- `owned_card()` читает точную карточку по `task_id`, поэтому ранее показанный
  callback не зависит от страницы в 20 элементов;
- `resolution_reason` проходит через persistence, application outcome,
  идемпотентный receipt и точный Telegram-текст;
- немедленная отмена после освобождения слота пишет `task_cancelled` audit от
  имени автора.

- migration head — `0017`; upgrade, empty cycle и legacy cycle пройдены.

## Отклонения от плана

- Для smoke-тестов локальный editable-пакет был явно установлен через
  `uv pip install -e .`, а `.venv/Scripts` добавлен в `PATH`; без этого
  `shutil.which` не видит console scripts в неактивированном PowerShell.
- Старый exact migration test больше не запускает актуальный application-код на
  намеренно откатанной схеме `0012`: данные создаются на head, после чего отдельно
  проверяется требуемый цикл `0012 -> 0011 -> 0012`.
- Автоматическое определение начала работы не добавлялось: до submit решение
  принимает сам исполнитель кнопкой «Уже начал(а)».

## Эскалационное исключение

Третья проверка вернула `changes_requested`. Владелец явно разрешил продолжить:
устаревший assertion обновлён под `obsolete/work_started`, добавлен полный
многоместный конкурентный oracle, выполнены затронутый и полный gate. До
дополнительного независимого review PR и deploy оставались закрыты. Попытка 4,
явно разрешённая владельцем, завершилась `Status: approved` без P0-P3 findings.

## Оставшиеся проверки

- PR, успешный CI и merge в `main`;
- сборка и deploy точного release digest на production;
- живая Telegram-проверка компактной карточки, `+/-`, свободной отмены и обоих
  исходов занятой отмены с отдельной разрешённой пользовательской сессией;
- production health bot/worker/PostgreSQL и отсутствие failed outbox events.

Отсутствие второй разрешённой живой Telegram-сессии блокирует завершение
занятого сценария и не может быть заменено прямым изменением БД.
