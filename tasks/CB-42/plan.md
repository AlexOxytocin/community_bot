# CB-42 — план реализации

## Цель

Заменить пользовательское создание задания по фиксированному шаблону на свободную, но строго структурированную форму в Telegram: тип, категория, размер времени, число исполнителей, награда, название, описание, критерии, материалы, предпросмотр, публикация и досрочное завершение набора.

## Область изменений

- Доменные правила создания пользовательского задания.
- PostgreSQL-схема `task_creation_drafts` и `tasks`.
- Прикладной сервис `TaskService` и связанные persistence-функции.
- Telegram-интерфейс создания задания и подсказки.
- Поведение завершения набора группового задания.
- Документация MVP и журнал решений.
- Целевые unit/integration/output-driven тесты.

## Вне области изменений

- WebApp с настоящим live-счётчиком символов.
- Полная замена административного сценария заданий сообщества.
- Удаление исторического каталога `task_templates`.
- Новая обязательная модерация всех свободных заданий.
- Изменение правил начисления опыта, кармы и споров после сдачи результата.
- Production deploy и живой Telegram-smoke до merge.

## Текущее состояние

Пользовательское создание задания зависит от `task_templates`: черновик хранит `template_id`, публикация копирует стоимость, название, описание и критерии из шаблона, а результат проверяется по `template.result_schema`. В базе `template_id` обязателен, а число исполнителей ограничено `1..10`.

Отмена занятого задания сейчас означает запрос на отмену всем `accepted` исполнителям. Если кто-то отказал, задание остаётся активным для всех, включая новых исполнителей. Это противоречит новой модели «завершить набор, но не обнулить тех, кто уже работает».

## Предлагаемое решение

### Схема данных

Добавить в `task_creation_drafts` поля снимка свободной карточки:

```text
category_id NULL
task_kind NULL                 # solo | group
time_size NULL                 # xs | s | m | l | xl
title NULL
description NULL
completion_criteria NULL
credit_reward_per_performer NULL
estimated_minutes NULL
```

Сделать `task_creation_drafts.template_id` nullable. Для новых пользовательских заданий `template_id = NULL`, для старых и совместимых community-путей значение сохраняется.

Сделать `tasks.template_id` и `tasks.template_version` nullable. Старые опубликованные задания сохраняют значения, новые свободные задания публикуются без шаблона.

Добавить в `tasks`:

```text
time_size NULL
closed_for_new_performers_at NULL
```

Состояние `closed_for_new_performers` в `TaskStatus` добавлять как отдельный статус. Оно будет:

- скрывать карточку из доступного каталога;
- запрещать новый acceptance даже по старому callback;
- оставлять активные назначения в обычном lifecycle.

Расширить `ck_tasks_status` и immutable trigger: разрешить менять `status`, `cancelled_at`, `closed_for_new_performers_at`, `updated_at` и, только если нужно для состояния, не менять снимок карточки.

Снять верхний лимит `10` с `performer_slots` для пользовательских заданий:

- draft/tasks check: `performer_slots > 0`;
- community/task-template старые ограничения оставить в логике community/templates, где они ещё нужны;
- итоговый резерв и доступный баланс остаются фактическим ограничителем.

### Категории

Обновить seed каталога новой версией/миграцией:

```text
promotion               📣 Продвижение
evaluation_testing      🔍 Оценка и тестирование
communication           💬 Коммуникация
learning_review         🎓 Обучение и разбор
practical_help          🤝 Практическая помощь
other                   🧩 Другое
community_development   🌱 Развитие комьюнити
```

Добавить в категорию конфигурационный/DB-флаг видимости, минимально через `visibility` или `admin_only`. Если делать без нового поля, придётся зашить `community_development` в код, что хуже. Предлагаемый вариант: `task_categories.visibility TEXT NOT NULL DEFAULT 'public' CHECK visibility IN ('public','admin_only')`.

Inline-меню показывает только активные категории, доступные актору. `community_development` доступна только active administrator.

### Размеры и награды

Добавить доменные правила:

```text
⚡ XS: до 15 минут, награда 1 или 2
⭐ S:  15-40 минут, награда 2, 3 или 4
💎 M:  40-75 минут, награда 4, 5, 6 или 7
🏆 L:  75-120 минут, награда 6, 7, 8, 9 или 10
👑 XL: больше 120 минут, любое целое число > 10
```

`estimated_minutes` хранить как верхнюю границу для диапазона: `15`, `40`, `75`, `120`, для `XL` — `121` как минимальный технический маркер. Отображение делает presenter по `time_size`, а не по числу минут.

### Мастер создания

Новые шаги:

```text
task_kind
category
time_size
performer_slots
reward
title
description
completion_criteria
materials
deadline
format
preview
published
```

`deadline` и `format` сохраняются из старого сценария, потому что они нужны опубликованной карточке и текущим проверкам дедлайна/формата.

Для `solo` `performer_slots = 1`, шаг числа исполнителей пропускается. Для `group` бот принимает любое целое число `> 1`, а итоговая стоимость проверяется после выбора награды и снова при публикации.

Текстовые лимиты:

```text
title: 80
description: 1200
completion_criteria: 700
materials.text: 1000
```

Материалы опциональны: кнопка `Пропустить` сохраняет `{"text": "Дополнительные материалы не требуются"}`. URL и схемы в тексте продолжают проходить `validate_public_text_uris`.

### Предпросмотр и редактирование

Предпросмотр показывает все поля и полный резерв:

```text
💎 M · 40-75 минут
Категория: 🔍 Оценка и тестирование
Тип: групповое
Исполнителей: 3
Награда: 6 кредитов за исполнителя
К резервированию: 18 кредитов
```

Кнопки редактирования строятся короткими callback:

```text
[ Тип ] [ Категория ] [ Время ]
[ Исполнители ] [ Награда ]
[ Название ] [ Описание ]
[ Критерии ] [ Материалы ]
[ Срок ] [ Формат ]
[ Опубликовать ]
[ Отменить ]
```

Редактирование пункта переводит draft на соответствующий шаг, увеличивает revision и сохраняет idempotent update receipt. Если изменение влияет на зависимые поля, например размер меняет допустимую награду, награда сбрасывается.

### Публикация

При публикации повторно проверять:

- actor существует, active и не ограничен на `CREATE_TASK`;
- category активна и доступна роли;
- `task_kind`, `time_size`, `performer_slots`, reward валидны;
- `title`, `description`, `completion_criteria`, `materials`, `deadline`, `format` заполнены и валидны;
- `reserved_credit_total = performer_slots * credit_reward_per_performer`;
- доступного баланса хватает на полный резерв;
- replay по `publish_command_id` не создаёт повторную карточку и повторный ledger.

Для свободных пользовательских заданий `safety_snapshot_json` хранит:

```json
{
  "task_kind": "...",
  "time_size": "...",
  "category_code": "...",
  "category_name": "...",
  "performer_instructions": "Следуйте описанию задания и критериям результата.",
  "public_input_keys": ["description"]
}
```

`input_payload_json` хранит безопасный дублирующий контекст `{"description": "..."};` он нужен для существующих карточек/презентеров. Result validation для свободных заданий принимает стандартную закрытую схему с одним текстовым полем результата вместо исторического template schema.

### Завершение набора

Переименовать пользовательскую кнопку для групповых active-заданий:

```text
[ Завершить набор ]
```

Поведение:

- если нет активных исполнителей, задание отменяется сразу и весь резерв возвращается;
- если есть активные исполнители, задание переходит в `closed_for_new_performers`, `closed_for_new_performers_at` заполняется, свободные слоты возвращаются автору одним idempotency key;
- новые acceptance/listing используют только `status='published'`, поэтому закрытое задание недоступно новым исполнителям;
- для `accepted` исполнителей создаются cancellation responses с кнопками `Согласен отменить` и `Сдать результат`;
- отказ исполнителя больше не возвращает задание в активный каталог, а только сохраняет его активное assignment-право;
- согласие исполнителя отменяет его assignment и возвращает резерв ровно за один слот;
- если после согласий не осталось активных assignments, task становится `cancelled`;
- если активные assignments остались, task остаётся `closed_for_new_performers` до финального расчёта;
- `_update_task_aggregate` должен учитывать `closed_for_new_performers`: если новых слотов уже быть не может и активных assignments нет, итог выводится из фактически оплаченных/терминальных слотов, а не из исходного `performer_slots`.

## Ключевые решения и альтернативы

- `template_id` делаем nullable, а не создаём синтетический шаблон `free_form`. Синтетический шаблон вернул бы старую зависимость под другим именем и сделал бы категории/награду мутными.
- Новое состояние `closed_for_new_performers` лучше отдельного boolean-флага при `published`, потому что существующий acceptance уже централизованно проверяет статус. Это дешевле и безопаснее, чем помнить про флаг во всех местах.
- Категории остаются в таблице `task_categories`, а не только в product config JSON. Таблица уже является рабочим справочником и связана с published tasks.
- Полностью удалять старый `/task_create <template_id>` не нужно в этой задаче. Если команда получает template id, можно вернуть понятную ошибку или создать legacy draft только для внутренних тестов. Пользовательский `/create` и `/task_create` без id идут по новой форме.

## Риски и меры снижения

- Риск двойного резерва при publish replay: сохранить `publish_command_id`, command gate и ledger idempotency key.
- Риск поломать старые задания: `template_id` nullable только для новых свободных задач, mapper и result validation обрабатывают оба режима.
- Риск бесконечного группового задания с огромным числом исполнителей: публикация ограничена доступным резервом автора; при положительной награде это реальный верхний предел.
- Риск неочевидного закрытия набора: в UI писать именно «Завершить набор», а не «Отменить», и объяснять последствия перед подтверждением.
- Риск слишком широкой категории `Другое`: в подсказке честно указывать, что это fallback, если задача не ложится никуда нормально.
- Риск Telegram-счётчика символов: не обещать live-счётчик, валидировать после отправки и возвращать точное превышение.
