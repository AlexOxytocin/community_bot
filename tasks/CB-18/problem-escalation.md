# CB-18 — эскалация двух непройденных ревью плана

Режим: `review_cycle`.

## Попытки

- `reviews/plan/attempt-01.md` — `Status: changes_requested`;
- `reviews/plan/attempt-02.md` — `Status: changes_requested`.

## Общая причина

Первый план пытался формализовать процесс слишком подробно и превратил
небольшое правило MVP в тяжёлую систему gates, истории и машинных контрактов.
Кроме того, полная регрессия была ошибочно поставлена перед final review каждой
задачи. Это противоречит цели владельца сократить накладные расходы.

## Собранные замечания

- сохранить обе попытки и не сбрасывать счётчик сменой файла;
- не смешивать два review с тремя техническими попытками;
- запускать review только на полном результате, а не на узких слайсах;
- задать понятную границу крупной задачи;
- не выдавать index tree за детектор изменений working tree;
- не создавать тест, который проверяет самостоятельно придуманную YAML-схему.

## Решение владельца

Процесс должен быть разумным для MVP чат-бота. Полный код задачи сначала
доводится до готовности и проходит целевые проверки, затем выполняется final
review. Полная регрессия проводится отдельно после готовности всего MVP.
Процессные накладные расходы обычной задачи должны быть существенно меньше
времени разработки.

## Одно консолидированное исправление

- убрать YAML-реестр, SHA-каталог, новую Python-зависимость и процессный unit test;
- оставить простые immutable Markdown attempts и один escalation-файл;
- перенести общую регрессию в отдельную финальную задачу MVP;
- обновить канонические документы и процедуры ролей одним проходом;
- после готовности результата выполнить одну финальную проверку, без третьего
  обычного plan-review.
