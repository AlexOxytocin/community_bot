# CB-35 - план проверки

## Автоматические проверки

1. Красный регрессионный сценарий проходит создание по видимым кнопкам и проверяет,
   что предпросмотр содержит описание автора, критерий и URL.
2. После публикации другой участник открывает «Найти задание» и видит те же данные.
3. После нажатия «Взять» подтверждение содержит полный контекст и кнопки действий.
4. Одинаковые значения payload выводятся один раз.
5. Длинные значения не создают сообщение больше 4096 символов.
6. Текст с HTML-подобными символами отправляется без parse mode.
7. Групповой чат не получает полную карточку и не может принять задание.
8. `tg://`, `file://`, `intent://` и URL со встроенными credentials отклоняются.
9. Карточка содержит инструкции исполнителю и точное имя автора.
10. Автор видит полную карточку в «Моих заданиях».
11. Старые опубликованные снапшоты не выводят опасные URI и сохраняют поля
    произвольной прежней input-схемы.
12. Обычный текст, `/cancel`, «Мои задания» и community-task navigation не
    продолжают task flow из группового чата.

## Регрессия

- целевые unit/integration/output-driven тесты Telegram;
- `ruff format --check`, `ruff check`, `ty check`, `git diff --check`;
- полный `pytest` перед merge.

## Production-проверка

После merge и deploy открыть `@humanquest_bot` канонической пользовательской
сессией, нажать «Найти задание» и проверить карточку опубликованного задания
«Проверка лендинга»: видны авторский текст, критерий результата и ссылка. Затем
принять свободное тестируемое задание только если это не меняет чужой рабочий
сценарий; иначе подтверждение принятия доказывается output-driven E2E, а живой
smoke ограничивается чтением карточки.
