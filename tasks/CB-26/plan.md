# CB-26 — план исправления timezone UX

## Цель

Убрать технический IANA-вопрос из обычной регистрации. Сохранять timezone
отдельно для локальных уведомлений, но определять его автоматически по
однозначному городу.

## Изменения

1. Добавить детерминированный resolver без внешнего API:
   - нормализовать пробелы, дефисы, подчёркивания, регистр и диакритику;
   - поддержать русские названия основных городов пилота;
   - сопоставлять латинское название с последним компонентом pinned tzdata;
   - принимать один timezone либо alias из явной canonical-карты пилотных городов;
   - при любых нескольких динамических совпадениях возвращать `None`, не пытаясь
     доказывать эквивалентность эвристикой по offsets.
2. После ответа `city`:
   - сохранить city;
   - при успешном resolve в той же транзакции сохранить timezone и перейти сразу
     к `short_bio`;
   - иначе оставить шаг `timezone`.
3. На ручном шаге timezone принимать exact IANA identifier или обычное название
   города (`Buenos Aires`, `Москва`).
4. Заменить технический prompt понятной fallback-инструкцией.
5. Добавить production-composed Telegram сценарий с человеческим вводом и
   regression test для уже существующего draft на timezone step.
6. Синхронизировать пользовательский flow и интерфейс бота в документации MVP.

## Не входит

- внешний geocoding API и справочник всех населённых пунктов мира;
- определение timezone только по свободному неоднозначному названию;
- изменение схемы БД или времени уже созданных событий.

## Проверка

- unit resolver/normalization;
- registration integration и production-composed Telegram tests;
- replay/stale-step/idempotency regression;
- Ruff, ty и один независимый final review готового diff;
- полная регрессия MVP не повторяется.
