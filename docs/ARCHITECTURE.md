# Архитектура

## Статус

Предварительные границы до утверждения продуктовых требований.

## Базовый подход

Для первой версии предпочтителен небольшой модульный монолит со следующими логическими слоями:

1. Telegram transport — получение обновлений и формирование ответов.
2. Application — пользовательские сценарии и координация операций.
3. Domain — правила комьюнити, роли и состояния.
4. Infrastructure — база данных, очереди и внешние интеграции.

Это логические границы, а не требование создавать отдельный сервис для каждого слоя.

## Ограничения

- Telegram-обработчики не должны содержать бизнес-правила.
- Доменная логика не должна зависеть от конкретной Telegram-библиотеки.
- Внешние интеграции должны иметь явные интерфейсы и контролируемые таймауты.
- Повторная доставка Telegram update не должна приводить к повторному необратимому действию.
- Секреты и пользовательские сессии находятся за пределами репозитория.
- Сбор персональных данных ограничивается минимумом, необходимым для функций бота.

## Выбор технологий

Язык, Telegram-фреймворк, база данных и хостинг будут выбраны после фиксации сценариев, нагрузки и требований к эксплуатации.
