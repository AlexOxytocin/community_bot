# Архитектура

## Статус

Целевая архитектура MVP с реализованным фундаментом участников, авторизации,
аудита, дедупликации Telegram updates и транзакционным ядром экономики с
версионной продуктовой конфигурацией. Остальные продуктовые сценарии
добавляются последующими задачами.

## Базовый подход

Для первой версии предпочтителен небольшой модульный монолит со следующими логическими слоями:

1. Транспортный слой Telegram — получение обновлений и формирование ответов.
2. Прикладной слой — пользовательские сценарии и координация операций.
3. Доменный слой — правила комьюнити, роли и состояния.
4. Инфраструктурный слой — база данных, очереди и внешние интеграции.

Это логические границы, а не требование создавать отдельный сервис для каждого слоя.

## Ограничения

- Telegram-обработчики не должны содержать бизнес-правила.
- Доменная логика не должна зависеть от конкретной Telegram-библиотеки.
- Внешние интеграции должны иметь явные интерфейсы и контролируемое предельное время ожидания.
- Повторная доставка обновления Telegram не должна приводить к повторному необратимому действию.
- Гарантия обработки update ограничена одним зафиксированным доменным эффектом PostgreSQL. Вызов Bot API выполняется только после commit и может безопасно повториться; точная граница зафиксирована в [ADR-0006](adr/0006-telegram-update-transaction-boundary.md).
- Секреты и пользовательские сессии находятся за пределами репозитория.
- Сбор персональных данных ограничивается минимумом, необходимым для функций бота.
- Jira используется для инженерной координации и не считается рабочей шиной бота без отдельного ADR.
- Будущие роли искусственного интеллекта проектируются вокруг ограниченных способностей, а пользовательские сценарии собираются из этих способностей на уровне оркестрации.

## Выбор технологий

Утверждён стек Python 3.13, aiogram 3.x, PostgreSQL 18, SQLAlchemy 2 async, asyncpg и Alembic. Зависимости управляются через uv; проверки выполняют Ruff, ty и pytest. Полное решение: [TECH_STACK.md](mvp/TECH_STACK.md) и [ADR-0005](adr/0005-mvp-technology-stack.md).

Бот и worker запускаются отдельными процессами из одной кодовой базы. Фоновые операции используют PostgreSQL outbox; внешний брокер сообщений для MVP не применяется. Telegram updates принимаются через long polling.

Конкретный провайдер размещения остаётся открытым эксплуатационным решением.

## Экономика и продуктовая конфигурация

`account_transactions` является неизменяемым источником истины для кредитов и
опыта. Кэши участника обновляются в той же PostgreSQL-транзакции и могут быть
проверены read-only сверкой с суммой журнала. Публичный прикладной порт принимает
полный batch именованных операций без скрытого commit, поэтому будущий workflow
задания сможет сохранить своё состояние, проводки и audit одним unit of work.

Идемпотентность обеспечивается advisory locks по полным бизнес-ключам и точной
проверкой канонического payload. Строки участников и исходные проводки разворота
блокируются в детерминированном порядке. Повтор всего batch допустим только если
сохранены все его операции с теми же payload; смешанный повтор отклоняется.

Редактируемый файл `config/product-config.v1.json` проходит строгую проверку, но
не является runtime-источником истины. После ingest и активации им становится
неизменяемая версия в PostgreSQL. Переключение активной версии, история
активации и синхронный backfill кэшей уровня фиксируются одной транзакцией.
`LevelResolver` всегда использует точную активную версию и не доверяет кэшу от
другой версии.
