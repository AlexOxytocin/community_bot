# План тестирования

## 1. Уровни тестов

- unit: правила и переходы состояний;
- integration: база, транзакции, Telegram adapters;
- end-to-end: пользовательские сценарии через тестового бота;
- migration: обновление пустой и заполненной базы;
- pilot checks: продуктовые и антифрод-сигналы.

## 2. Регистрация

- действующее приглашение принимается один раз;
- отозванное и просроченное приглашение отклоняется;
- повторный `/start` не создаёт второго участника;
- прерванная регистрация продолжается;
- после первого одобрения начисляется ровно `10` кредитов и `0` опыта;
- два конкурентных одобрения и повтор после перезапуска создают одну операцию
  `starting_grant` и возвращают сохранённый исход;
- release-backfill создаёт отсутствующий `starting_grant` только active-участникам
  и не дублирует существующие стартовые проводки;
- неподтверждённый пользователь не создаёт задания;
- изменение username не создаёт новый аккаунт.

## 3. Каталог

- неактивная категория скрыта;
- неподходящий уровень блокирует шаблон;
- версия шаблона фиксируется в задании;
- изменение цены влияет только на новые задания;
- обязательные поля валидируются;
- пагинация не пропускает и не дублирует записи.
- новая версия уже показанного `template.code` не повторяет его на следующей
  keyset-странице;
- input/result payload проверяются по точной исторической JSON Schema до
  передачи следующей доменной команде;

## 4. Создание задания

- недостаточный баланс блокирует публикацию;
- резерв создаётся один раз;
- повторный callback не создаёт второе задание;
- отмена возвращает правильную сумму;
- прошедший срок не допускается;
- автор не может взять собственное задание.
- черновик восстанавливается после создания нового service/router и продолжает
  работу с сохранённого шага;
- два черновика одного автора с разными ключами при одновременной публикации и
  балансе на один резерв дают ровно одно полное задание и неотрицательный баланс;
- публикация фиксирует task, ledger reserve, audit, outbox и Telegram receipt
  одной транзакцией; ошибка не оставляет ни одного частичного эффекта;
- повторная и конкурентная отмена создаёт один точный refund с нулевым опытом;
- неизменяемый снимок опубликованного задания нельзя изменить или удалить
  прямым SQL.

## 5. Выполнение

- два пользователя не занимают единственное место одновременно;
- превышение лимита активных заданий блокируется;
- результат версионируется;
- нельзя отправить результат отменённого задания;
- нельзя подтвердить результат дважды;
- частичное выполнение запрещено при награде `1`; награды `2/3/4/5/11` дают
  `1/2/2/3/6` кредитов и столько же опыта;
- спор замораживает выплату.

## 6. Кредиты и опыт

Для каждого сценария проверять журнал и кэш:

```text
стартовый грант: credits +10, experience +0
выполнение: credits +N, experience +N
создание: credits -N, experience +0
возврат: credits +N, experience +0
аннулирование: обратная операция
```

Обязательные проверки:

- сумма журналов равна кэшу;
- повторный idempotency key не создаёт операцию;
- опыт не уменьшается при трате;
- лидерборд сортируется по опыту, не по балансу;
- для порогов `10/25/50/100/180/300/450/650/1000` значения `threshold-1` и
  `threshold` дают соседние уровни, а опыт выше `1 000` остаётся на уровне 10;
- устаревшая версия кэша не влияет на профиль, минимальный уровень, принятие,
  лидерборд и уведомления; повторный или прерванный backfill идемпотентен;
- конкурентные чтение и активация конфигурации не наблюдают смешанную шкалу.

## 7. Карма

- самооценка запрещена;
- допустимы только `-1`, `0`, `1`;
- комментарий обязателен и валидируется;
- повторная оценка обновляет запись, а не создаёт вторую;
- изменение `+1` на `-1` меняет агрегат на `-2`;
- получатель и любой модератор видят только aggregate/count без raw fields;
- active administrator без `karma_review` получает отказ, а с правом видит raw
  data и создаёт audit просмотра;
- первая ненулевая full/partial выплата между парой даёт eligibility в обоих
  направлениях; community-task, cancel, reject, `no_show` и unresolved dispute
  его не дают;
- eligibility сохраняется после correction/reversal экономики, но mutation
  запрещена, если хотя бы один участник не `active`;
- изменение статуса не стирает current vote и immutable history;
- moderator не получает raw data через поддельный callback или клиентский
  permission token;

## 8. Авторизация

- участник не открывает admin menu поддельным callback;
- модератор не меняет глобальные настройки без права;
- заблокированный пользователь не создаёт и не принимает задания;
- пользователь не читает чужую историю кредитов;
- пользователь не читает авторов своей кармы;
- active-пользователь видит safe projection каждого active-профиля, но не видит
  чужие `pending`, `paused`, `restricted`, `suspended`, `left`, `banned` ни в
  каталоге, ни по UUID;
- каталог участников отображается одним компактным сообщением, показывает
  каждую строку участника отдельной inline-кнопкой, раскрывает одну строку через
  `+`/`-` и сохраняет действия внутри раскрытой строки;
- поиск участников принимает минимум 3 символа, ищет по публичным
  `telegram_username`/`display_name` и не возвращает non-active профили;
- собственный профиль доступен при `active`/`paused`; остальные статусы и
  индивидуальные ограничения `restricted` соблюдаются сервером;
- administrator без/с `member_read` соответственно не читает/читает
  non-active safe projection;
- stale cursor и конкурентная смена target status не обходят профильную policy
  и не раскрывают существование скрытой записи;
- идентификаторы из callback проверяются на принадлежность.

## 9. Конкурентность

Проверить параллельные запросы:

- два принятия последнего места;
- два подтверждения результата;
- отмена одновременно с принятием;
- списание одновременно с публикацией двух заданий;
- два изменения одной оценки кармы;
- повторная доставка Telegram update после timeout.

Дополнительно сериализуются: первая отправка результата и истечение слота;
спор и граничный финализатор; спор и автоподтверждение; пересечение порога пары;
повтор полной, частичной или системной выплаты задания сообщества.

## 10. Уведомления

- дедупликация;
- повтор после временной ошибки;
- отсутствие повторной отправки после успеха;
- корректный часовой пояс;
- уведомление не изменяет доменное состояние.

## 11. Принятые правила экономики и жизненного цикла

### Конфигурация уровней

- повтор `version + hash` создаёт одну неизменяемую версию; коллизия номера или
  тот же снимок под новым номером отклоняются;
- повтор одной команды активации даёт один указатель, аудит и backfill; та же
  команда с другой целью отклоняется;
- откат выполняется новой командой к старой версии, его повтор безопасен;
  активация уже активной версии не запускает backfill;
- невалидная активация или startup-кандидат сохраняют текущую активную версию;
  первый запуск без валидного кандидата запрещён.

### Истечение, проверка и частичная выплата

- незанятые, занятые без результата и отправленные слоты многоместного задания
  разрешаются независимо; агрегат проходит `settling` и получает один корректный
  терминальный статус;
- отправка за микросекунду до дедлайна допустима, на границе запрещена; гонка с
  истечением даёт ровно возврат/`no_show` либо сохранённый расчёт для проверки;
- поздняя коррекция `no_show` добавляет событие, не удаляет историю и не создаёт
  скрытую выплату;
- ручное решение допустимо за микросекунду до `72h`, на границе действует один
  autoconfirm; новые версии не сдвигают срок, решения подавляют напоминания;
- отклонение отменяет обычный autoconfirm и открывает отдельные `24h`; спор
  допустим до границы даже после исходных `72h`, на границе выполняется один
  возврат или закрытие без выпуска;
- у задания участника частичная выплата плюс возврат исчерпывают резерв слота; у
  задания сообщества выпускается только фактическая сумма без личного резерва.

### Алерты и штрафы

- любое число валидных взаимодействий пары можно принять и оплатить: частота не
  создаёт отказ, откат выплаты или автоматический штраф;
- при пороге `3` первые три оплаченных полных/частичных задания участника не
  создают алерт, четвёртое в `(T-7 суток,T]` создаёт один; нижняя граница
  исключена, направление, категория и версия шаблона пару не разделяют, задания
  сообщества не считаются;
- блокировка пары не теряет пересечение. Открытый алерт переживает смену политики
  и записывает обе версии без дубля; после закрытия повторный эпизод появляется
  только после спада до порога и нового пересечения; `threshold=0` отключает
  новые алерты;
- только активный администратор с `interaction_review` читает и закрывает алерт;
  участник и модератор не видят приватные пояснения;
- `legitimate` и `monitor` не создают операций. Только `penalty_recommended`
  допускает один штраф на участника и алерт; повтор бизнес-ключа безопасен,
  превышение доступного нерезервированного баланса откатывает весь исход.

### Задания сообщества

- участник и модератор не создают `origin=community`; уполномоченный активный
  администратор создаёт неизменяемую карточку, видимую как «Сообщество»;
- отсутствующий или непроверяемый результат, неограниченный объём, время более
  `120` минут, обязательный лайк, подписка, положительный отзыв, endorsement или
  нарушение правил площадки отклоняются;
- награда выше `4` без обоснования и второго подтверждения отклоняется, корректное
  исключение аудируется и не меняет опубликованный снимок;
- до принятия разрешена административная отмена; после принятия и до отправки —
  только по вине сообщества или системы с причиной, аудитом, уведомлением и
  апелляцией; после отправки, в проверке, споре и терминальном состоянии отмена
  запрещена;
- проверяющий не становится исполнителем, исполнитель-администратор не проверяет
  и не отменяет. Недействительный проверяющий даёт `reviewer_required` без
  выпуска; независимая замена открывает новые `72h` с `24/48`, добровольная
  замена действительного проверяющего срок не продлевает;
- полная, частичная и повторная обработка создают одну
  `community_task_reward` с равным опытом; отклонение, отмена и истечение не
  выпускают кредиты, а спор блокирует выпуск до решения.

## 12. Приёмочные сценарии

### Сценарий A: полный обмен

1. Администратор приглашает A и B.
2. Оба регистрируются.
3. A публикует задание за 2 кредита.
4. B принимает и отправляет результат.
5. A подтверждает.
6. Баланс A уменьшен на 2.
7. Баланс и опыт B увеличены на 2.
8. Лидерборд отражает опыт B.

### Сценарий B: отмена

1. A публикует задание.
2. Никто его не берёт.
3. A отменяет.
4. Резерв возвращается.
5. Опыт A не меняется.

### Сценарий C: спор

1. B отправляет результат.
2. A открывает спор.
3. Выплата заморожена.
4. Модератор выбирает частичную оплату.
5. Журнал и статусы отражают решение.

### Сценарий D: карма

1. A ставит B `+1` с комментарием.
2. B видит изменение агрегата без автора.
3. A меняет оценку на `-1`.
4. Агрегат корректно меняется.
5. Администратор видит обе версии.

## 13. Готовность к пилоту

- все приёмочные сценарии автоматизированы либо имеют воспроизводимый чек-лист;
- нет открытых критических дефектов;
- выполнено восстановление локального backup в новую изолированную PostgreSQL и
  проверены Alembic revision, ключевые таблицы и оба process readiness;
- проверена сверка журнала;
- подготовлены тестовые шаблоны;
- Sentry принимает очищенное исключение с release/correlation context и не
  принимает Telegram payload, секреты, invite-коды, evidence или приватные
  комментарии;
- подтверждены bounded Docker logs, семидневное хранение локальных backup,
  `RPO <= 24h` и `RTO <= 4h` реальным drill до запуска пилота.

Перед общей регрессией CB-16 цикл назначения отдельно проверяется на PostgreSQL:
конкуренция последнего места и лимита `3`, replacement отменённого слота,
append-only версии результата, exactly-once полная/частичная выплата, приватный
dispute handoff, correlated ledger rows и миграционный цикл `0006↔0007`.
