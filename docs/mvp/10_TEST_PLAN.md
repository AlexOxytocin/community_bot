# План тестирования

## 1. Уровни тестов

- unit: правила и переходы состояний;
- integration: база, транзакции, Telegram adapters;
- end-to-end: пользовательские сценарии через тестового бота;
- migration: обновление пустой и заполненной базы;
- pilot checks: продуктовые и антифрод-сигналы.

## 2. Регистрация

- действующее приглашение принимается один раз;
- отозванное и просроченное приглашение отклоняется;
- повторный `/start` не создаёт второго участника;
- прерванная регистрация продолжается;
- стартовые кредиты начисляются ровно один раз;
- неподтверждённый пользователь не создаёт задания;
- изменение username не создаёт новый аккаунт.

## 3. Каталог

- неактивная категория скрыта;
- неподходящий уровень блокирует шаблон;
- версия шаблона фиксируется в задании;
- изменение цены влияет только на новые задания;
- обязательные поля валидируются;
- пагинация не пропускает и не дублирует записи.

## 4. Создание задания

- недостаточный баланс блокирует публикацию;
- резерв создаётся один раз;
- повторный callback не создаёт второе задание;
- отмена возвращает правильную сумму;
- прошедший срок не допускается;
- автор не может взять собственное задание.

## 5. Выполнение

- два пользователя не занимают единственное место одновременно;
- превышение лимита активных заданий блокируется;
- результат версионируется;
- нельзя отправить результат отменённого задания;
- нельзя подтвердить результат дважды;
- частичное выполнение переводит утверждённую конфигурируемую долю;
- спор замораживает выплату.

## 6. Кредиты и опыт

Для каждого сценария проверять журнал и кэш:

```text
стартовый грант: credits +N, experience +0
выполнение: credits +N, experience +N
создание: credits -N, experience +0
возврат: credits +N, experience +0
аннулирование: обратная операция
```

Обязательные проверки:

- сумма журналов равна кэшу;
- повторный idempotency key не создаёт операцию;
- опыт не уменьшается при трате;
- лидерборд сортируется по опыту, не по балансу;
- уровень пересчитывается на границе порога;
- десятый уровень начинается с 1 000 опыта.

## 7. Карма

- самооценка запрещена;
- допустимы только `-1`, `0`, `1`;
- комментарий обязателен и валидируется;
- повторная оценка обновляет запись, а не создаёт вторую;
- изменение `+1` на `-1` меняет агрегат на `-2`;
- получатель не видит автора;
- администратор видит автора и историю;
- обычный модератор видит данные только при наличии разрешения;
- блокировка пользователя не стирает историю.
- разрешённый сценарием участник может оценить другого, а участник без требуемого допуска получает отказ согласно решению `Q-005`;

## 8. Авторизация

- участник не открывает admin menu поддельным callback;
- модератор не меняет глобальные настройки без права;
- заблокированный пользователь не создаёт и не принимает задания;
- пользователь не читает чужую историю кредитов;
- пользователь не читает авторов своей кармы;
- пользователь видит только профили, разрешённые правилом `Q-011`;
- идентификаторы из callback проверяются на принадлежность.

## 9. Конкурентность

Проверить параллельные запросы:

- два принятия последнего места;
- два подтверждения результата;
- отмена одновременно с принятием;
- списание одновременно с публикацией двух заданий;
- два изменения одной оценки кармы;
- повторная доставка Telegram update после timeout.

## 10. Уведомления

- дедупликация;
- повтор после временной ошибки;
- отсутствие повторной отправки после успеха;
- корректный часовой пояс;
- уведомление не изменяет доменное состояние.

## 11. Приёмочные сценарии

### Сценарий A: полный обмен

1. Администратор приглашает A и B.
2. Оба регистрируются.
3. A публикует задание за 2 кредита.
4. B принимает и отправляет результат.
5. A подтверждает.
6. Баланс A уменьшен на 2.
7. Баланс и опыт B увеличены на 2.
8. Лидерборд отражает опыт B.

### Сценарий B: отмена

1. A публикует задание.
2. Никто его не берёт.
3. A отменяет.
4. Резерв возвращается.
5. Опыт A не меняется.

### Сценарий C: спор

1. B отправляет результат.
2. A открывает спор.
3. Выплата заморожена.
4. Модератор выбирает частичную оплату.
5. Журнал и статусы отражают решение.

### Сценарий D: карма

1. A ставит B `+1` с комментарием.
2. B видит изменение агрегата без автора.
3. A меняет оценку на `-1`.
4. Агрегат корректно меняется.
5. Администратор видит обе версии.

## 12. Готовность к пилоту

- все приёмочные сценарии автоматизированы либо имеют воспроизводимый чек-лист;
- нет открытых критических дефектов;
- выполнено восстановление тестовой резервной копии;
- проверена сверка журнала;
- подготовлены тестовые шаблоны;
- определён канал сообщений об ошибках пилота.
