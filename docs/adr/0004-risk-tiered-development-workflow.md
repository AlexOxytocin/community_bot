# ADR-0004 — Пропорциональный процесс разработки и работа с Git

**Статус:** Принято

**Дата:** 2026-07-16

## Контекст

Community Bot начинает как небольшой проект одного владельца, но использует агентов, Jira и публичный репозиторий GitHub. Нужны прослеживаемость, независимая проверка и безопасные внешние изменения, однако обязательная интеграционная ветка и одинаково тяжёлый набор артефактов для любой правки создали бы лишнюю церемонию.

## Решение

Использовать три уровня процесса.

Дополнение от 2026-08-14: [ADR-0010](0010-small-bugfix-fast-lane.md) вводит
уровень `1B` для малых воспроизводимых багфиксов. Он не заменяет уровни ниже, а
добавляет быстрый путь между документационным уровнем 1 и обычной задачей
реализации уровня 2.

Дополнение от 2026-08-15: владелец закрепил Jira-first правило. Любой баг,
функция, пользовательская история, изменение runtime-поведения, workflow или
процесса разработки требует Jira-задачу `CB` и ветку `task/<ISSUE-KEY>`.
Уровень `1B` сокращает артефакты и промежуточные переходы, но не отменяет Jira и
ветку задачи.

Дополнение от 2026-08-15: каждая ветка, созданная для Jira-задачи, должна пройти
маршрут commit → push → pull request → CI/review → merge в `main`, если gate не
заблокирован. Это постоянное намерение владельца для задачных веток.

### Уровень 1. Малая документационная правка

- Задача Jira и артефакты задачи не обязательны только для неповеденческой
  документационной чистки, если она не является багом, функцией, изменением
  runtime, workflow или процесса разработки и пользователь дал ясное прямое
  поручение.
- Обязательны проверка языка, ссылок, форматирования, отсутствия секретов и точное описание изменения.

### Уровень 2. Обычная задача реализации

- задача Jira с областью изменений и критериями приёмки;
- `plan.md`;
- ветка `task/<ISSUE-KEY>` от актуальной `origin/main`;
- целевые тесты, необходимые интеграционные проверки области и проверка основного сценария; полная регрессия продукта проводится отдельно по ADR-0007 после готовности всего MVP;
- `implementation-report.md`;
- независимый `final-review.md`;
- запрос на слияние в `main`, проверки CI и merge после успешных gates; если
  gate заблокирован, merge не выполняется, а блокер фиксируется в Jira.

### Уровень 3. Задача повышенного риска

Архитектурная, интеграционная, затрагивающая безопасность, разрушительная или насыщенная источниками задача дополнительно требует:

В рамках этого процесса задача, насыщенная источниками, относится к уровню 3 и считается задачей повышенного риска для выбора артефактов и проверок.

- `plan-source-context.md` с пакетом источников;
- независимый `plan-review.md` со `Status: approved`;
- ADR для структурного или сквозного решения;
- ручной `test-plan.md`, если автоматические тесты не доказывают пользовательский сценарий;
- усиленные специальные проверки домена.

Текущий процесс Git: `task/CB-N` → запрос на слияние → `main`. Ветка `dev` не создаётся заранее. Её введение требует отдельного ADR и реальной необходимости в параллельной интеграции или независимом цикле релизов.

## Рассмотренные альтернативы

Полный процесс `task → dev → main` для каждой задачи отклонён как преждевременный для проекта одного владельца. Прямая разработка в `main` без запроса на слияние и проверки отклонена из-за слабой прослеживаемости и риска смешения изменений. Одинаковый набор артефактов для опечатки в документации и архитектурной интеграции отклонён как непропорциональный.

## Последствия

- Небольшие неповеденческие документационные изменения не блокируются тяжёлым процессом.
- Малые воспроизводимые багфиксы могут использовать уровень `1B` из ADR-0010
  вместо полного набора артефактов уровня 2, но сохраняют Jira-задачу и ветку
  `task/<ISSUE-KEY>`.
- Изменения поведения сохраняют связь с задачей Jira, тесты и независимую проверку.
- Решения повышенного риска получают планирование на основе источников и ADR.
- `main` остаётся единственной стабильной веткой до появления обоснованной интеграционной ветки.
- Задачные ветки не остаются локальными или открытыми без причины: успешный gate
  ведёт к merge, заблокированный gate фиксируется в Jira.
- Существенное изменение разницы после проверки требует повторных тестов, обновления отчёта или compact bugfix note и новой проверки выбранного уровня риска.
