# 0022. Минимальный Telegram ingress и общие настройки

Статус: принято для локальной реализации; production activation — отдельный release.

Пользователь согласовал регистрацию по `/start` только для участников основного
чата и управление двумя подписками в боте и Mini App. Это расширяет прежний
web-only runtime, но не возвращает старый conversational task UI и polling.

- Один secret-checked webhook в существующем web service: `/start`,
  `/notifications`, private callbacks и новые сообщения одной настроенной темы.
- Telegram ID берётся из подписанного initData либо проверенного webhook.
  Только проверка членства разрешает упрощённое создание аккаунта; ошибки
  проверки не открывают доступ. Browser locale не подменяет UTC по умолчанию.
- Два режима одной регистрации. Singleton в PostgreSQL по умолчанию `standard`.
  Identity lock + ledger idempotency защищают одновременные bot/web входы.
  Статус active и грант 20 фиксируются одной транзакцией. Consent не выдумывается.
- Новые настройки пользователя хранятся отдельно от профиля. Оба интерфейса
  отправляют абсолютное значение и ожидаемую revision; устаревший callback
  не отменяет свежий выбор. `tasks=true`, `nomad=false` по умолчанию.
- Публикации только активного суперадминистратора без sender_chat. Идентификаторы
  чата/темы задаются конфигурацией. Outbox business key дедуплицирует сообщение
  либо альбом; исторические публикации до подписки не рассылаются. Privacy:
  не сохраняем полный текст поста или приватные сообщения пользователя.
- Очередь и отправитель повторно проверяют подписку. Отписка не отзывает уже
  отправленное сообщение; Telegram sendMessage не даёт строгого exactly-once
  при потере сетевого подтверждения. Business-level дедупликация гарантируется БД.
- Смена режима требует superserver permissions, revision, подтверждения и аудита.
  Начатые анкеты, блокировки и существующие профили автоматически не меняются.

## Выпуск и откат

1. Release с миграцией 0032 → 0033: остановка writers, fresh backup, isolated
   restore drill и exact readiness согласно проектному migration runbook.
   Новые таблицы не изменяют старые профили или ledger. Проверить downgrade на
   изолированной копии. В production не удалять настройки без отдельного решения.
2. Задать безопасный `TELEGRAM_WEBHOOK_SECRET`, основной чат/join URL/username,
   `NOMAD_TELEGRAM_CHAT_ID=-1002237685639`, `NOMAD_TELEGRAM_TOPIC_ID=24962`.
   Secret не попадает в лог, git или Jira. Endpoint без настройки отключён.
3. После deploy проверить canonical Telegram wrapper и фактический запуск из
   `@humanquest_bot`. Не использовать landing или прямой `/mini-app` как acceptance.
4. `python -m community_bot.bootstrap.telegram_features` делает read-only preflight.
   `--apply` — только после разрешения на Telegram mutation. Он не захватывает чужой
   webhook, не сбрасывает updates, сохраняет существующие команды и кнопку запуска
   Mini App. До изменения измерить и сохранить прежнее состояние вне репозитория.
5. Acceptance: член/не-член, стандартный/упрощённый вход, повторный `/start`,
   две панели подписок, реальный пост суперадминистратора и открытие его ссылки.
   Локальные mocks не заменяют эту проверку.
6. Операционный rollback: вернуть standard через UI; восстановить ранее
   измеренный webhook/commands и прежний runtime по согласованному release-плану.
   При откате к 0032 остановить новый ingress/worker до восстановления БД.
   Созданные аккаунты/20 кредитов не отменять автоматически. Начальные настройки
   миграции сами не включают упрощённый режим или рассылку.

## Активация на уже обновлённом runtime

`python3 -m ops.telegram_activation prepare` измеряет running image, release,
Compose labels, head 0033, права бота и прежний webhook/menu. Чужой webhook
блокирует активацию. Секрет создаётся на сервере, прежний и новый env сохраняются
root-private рядом с receipt, без вывода содержимого.

После проверки receipt: `python3 -m ops.telegram_activation apply --receipt PATH`.
Сценарий меняет только три Telegram-настройки, пересоздаёт worker/web с тем же
image и release, проверяет exact readiness, подключает webhook/команды и проверяет
публичный webhook запросами с неверным секретом и пустым Telegram update.
Меню запуска приложения, режим регистрации и подписки пользователей не меняются.
При сбое возвращаются env, webhook и команды; БД не восстанавливается.
После прерывания в фазе activating предусмотрен `recover --receipt PATH`.
Это транспортная проверка, а не пользовательская Telegram UI acceptance.

Сценарий также сохраняет измеренный nginx config и добавляет только exact location
`/api/telegram/webhook` внутри существующего host. Другие маршруты не меняются.
После пересоздания runtime выполняются `nginx -t` и reload; откат возвращает
прежний config вместе с env и командами. `status --receipt PATH` выводит только
безопасные идентификаторы и фазу операции, не содержимое приватных копий.
