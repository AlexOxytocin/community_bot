# ADR-0006 — Транзакционная граница обработки Telegram updates

**Статус:** Принято

**Дата:** 2026-08-10

## Контекст

Telegram может повторно доставить один update после timeout или разрыва соединения. Повтор не должен второй раз менять участника, создавать экономическую операцию или другое доменное действие. Память процесса не подходит для дедупликации: она теряется после перезапуска и не координирует несколько процессов.

PostgreSQL позволяет атомарно связать уникальный завершённый receipt update с доменным изменением. Однако Telegram Bot API находится вне транзакции PostgreSQL. Нельзя честно обещать exactly-once для внешней отправки или удерживать транзакцию БД во время сетевого вызова.

## Решение

Использовать в application-слое единый протокол обработки изменяющих Telegram updates.

1. `update_id` уникален глобально в пределах потока updates одного бота и является первичным ключом receipt в PostgreSQL.
2. Transport нормализует update до команды без выполнения Bot API и передаёт её application-слою.
3. Application открывает транзакцию и первой операцией получает transaction-scoped PostgreSQL advisory lock по детерминированному hash namespace `telegram_update` и `update_id`. Коллизия hash даёт только лишнюю сериализацию: duplicate всё равно определяется по точному первичному ключу receipt.
4. После lock application читает receipt. Если он существует, update является duplicate: сохранённый код результата возвращается без доменного изменения.
5. Если receipt отсутствует, application выполняет доменное изменение и audit, затем вставляет полностью заполненный receipt с `NOT NULL outcome_code/processed_at` и фиксирует всё одним commit.
6. Ошибка до commit откатывает доменное изменение, audit и receipt; transaction-scoped lock освобождается, поэтому повтор update может безопасно выполнить команду снова.
7. Гарантия «не более одного зафиксированного действия» относится только к эффектам PostgreSQL внутри этой транзакции.
8. Bot API вызывается только после commit. Transport формирует ответ из сохранённого кода результата. Для duplicate допустима повторная отправка того же безопасного ответа.
9. Потеря или повтор внешнего ответа остаются возможны. Критические исходящие уведомления в последующих задачах используют PostgreSQL outbox из ADR-0005; сетевой вызов внутрь доменной транзакции запрещён.
10. Все изменяющие обработчики используют порядок блокировок: advisory lock update, затем затрагиваемые доменные строки в стабильном порядке идентификаторов.

Для CB-6 receipt хранит `update_id`, тип update, nullable actor, обязательный код результата, `received_at` и обязательный `processed_at`. Полуготовый receipt никогда не вставляется. Все принятые transport updates, включая read-only `/start`, получают receipt и детерминированный outcome; update без пригодного actor отбрасывается до транзакции. Политика архивирования receipt определяется до пилота на основании фактического объёма; преждевременное удаление, допускающее повтор старого update, запрещено.

## Рассмотренные альтернативы

### In-memory set или TTL cache

Отклонено: состояние теряется после restart, не разделяется процессами и не атомарно с доменным действием.

### Ранний insert незавершённого receipt

Отклонено: обычные `CHECK/NOT NULL` нельзя отложить до commit, а отдельный constraint trigger с повторным чтением строки сложнее advisory gate и создаёт промежуточное состояние без пользы.

### Отдельный commit receipt до доменного изменения

Отклонено: ошибка после claim навсегда подавит retry и потеряет действие.

### Telegram-вызов внутри транзакции PostgreSQL

Отклонено: сетевой timeout удерживает блокировки, а успешную отправку нельзя откатить вместе с БД.

### Обещание exactly-once для Bot API

Отклонено как недостижимое без внешнего идемпотентного протокола. Для обычного ответа применяется at-least-once/best-effort, для будущих критических уведомлений — outbox.

### Немедленное введение отдельного брокера

Отклонено ADR-0005: PostgreSQL достаточно для транзакционного inbox/receipt и будущего outbox MVP.

## Последствия

Положительные:

- повтор и гонка одного update сериализуются до чтения receipt и не дублируют зафиксированное доменное действие;
- rollback сохраняет возможность retry;
- restart и несколько процессов используют одно состояние дедупликации;
- внешняя сеть не удерживает транзакцию и блокировки БД;
- граница гарантий проверяема и не маскирует ограничения Telegram.

Ограничения:

- безопасный пользовательский ответ может быть потерян или повторён;
- receipt-таблица растёт и требует политики хранения до пилота;
- результат изменяющей команды должен иметь сохраняемый детерминированный код;
- прикладные команды обязаны соблюдать единый порядок блокировок.
