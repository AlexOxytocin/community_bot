# ADR-0015 — Бюджетная многопоточная оркестрация агентов

**Статус:** Принято

**Дата:** 2026-08-16

## Контекст

Роли и независимые проверки полезны для сложных задач, однако существующий
процесс не ограничивает объём стартового контекста, повторные активации,
polling и передачу больших результатов инструментов. В одном запуске это
привело примерно к 3 100 модельным вызовам и 393 млн токенов. Формальное число
review-артефактов оставалось ограниченным, но одна попытка могла включать
десятки повторных turn и полную историю оркестратора.

## Решение

- По явному решению владельца после review escalation хранить модели,
  reasoning effort и execution budgets в глобальной политике
  `codex.agent-budget.v1`. Community Bot ссылается на policy/profile ids и не
  копирует эти значения.
- В `agents/config.yaml` хранить только project-specific document routing,
  карту ролей на global profiles, process/review, packet и tool-output budgets.
- Использовать Luna для разведки, ограниченной механической работы и дешёвых
  проверок состояния; Sol — для основной сложной реализации и независимого
  смыслового review. `xhigh` не является режимом по умолчанию.
- Ограничивать fan-out, descendant agents и follow-up значениями из
  `codex.agent-budget.v1`.
- Граф продолжения, progress evidence и его пределы хранить только в глобальной
  continuation policy; проект хранит точные ссылки и формат handoff packet.
- После жёсткого лимита не терять работу: сохранить компактный handoff и при
  необходимости продолжить в свежем контексте по решению корневого агента.
- Загружать только обязательное ядро документов; доменные, продуктовые,
  runtime- и role-specific источники подключать по условию задачи.
- Review получает Jira snapshot, критерии, diff, результаты тестов и ссылки на
  релевантные источники, а не полную историю диалога.
- Неизменившееся внешнее состояние проверять в пределах
  `codex.agent-budget.v1`. Далее
  использовать событийное ожидание или вернуть явный blocker.
- Ограничивать вывод инструментов; большие изображения анализирует один
  владелец, передавая остальным текстовое заключение.

## Рассмотренные альтернативы

Полный отказ от субагентов отклонён: он ухудшает независимость review и мешает
параллельной работе над действительно независимыми частями. Только более дешёвая
модель отклонена: основной расход создаёт повторный контекст и управляющие
циклы. Жёсткое завершение по времени без учёта прогресса отклонено: сложная
задача может быть близка к готовности и потеряет уже выполненную работу.

## Последствия

- Многопоточность сохраняется, но fan-out и управляющий трафик ограничены.
- Долгая полезная реализация может закончиться через progress extension или
  компактную передачу в свежий контекст.
- Review остаётся независимым, но читает меньший и проверяемый пакет.
- Числовые бюджеты становятся машиночитаемыми и проверяются CI.
- Global validator проверяет runtime consumers; project CI проверяет symbolic
  reference и отсутствие локальных копий execution budgets.
- Старые уже запущенные сессии не перенастраиваются ретроактивно.
- Перед merge процессной задачи проверяется отсутствие candidate-bound merge
  freeze другой активной задачи; при freeze разработка и review могут
  завершиться, но merge ожидает снятия gate.
