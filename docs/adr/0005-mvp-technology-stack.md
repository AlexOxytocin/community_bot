# ADR-0005 — Технологический стек MVP

**Статус:** Принято

**Дата:** 2026-08-10

## Контекст

Продуктовые требования MVP определены: закрытая регистрация, каталог фиксированных заданий, транзакционные кредиты, необратимо растущий опыт, изменяемая карма, лидерборд, модерация, споры и уведомления. Ошибка повторной обработки может привести к двойному начислению или нарушению анонимности, поэтому согласованность данных важнее возможности быстро распределить систему по сервисам.

Команда и ожидаемая пилотная нагрузка не требуют микросервисов или отдельного брокера. При этом бот должен поддерживать асинхронный Telegram transport и фоновые операции без блокировки пользовательских сценариев.

## Решение

Использовать Python 3.13 и модульный монолит со следующими основными компонентами:

- aiogram 3.x и `asyncio` для Telegram transport;
- PostgreSQL 18 как единственное транзакционное хранилище;
- SQLAlchemy 2.x async, asyncpg и Alembic для доступа к данным и миграций;
- Pydantic 2 и pydantic-settings для конфигурации;
- uv, `pyproject.toml` и `uv.lock` для воспроизводимого управления зависимостями;
- Ruff, ty, pytest, pytest-asyncio, Hypothesis и Testcontainers для контроля качества;
- стандартный `logging` со structlog для структурированных JSON-логов;
- Docker Compose для локальной среды и GitHub Actions для CI.

Бот в MVP получает updates через long polling. Фоновые уведомления и плановые операции выполняет отдельный worker из той же кодовой базы. Надёжная доставка строится на PostgreSQL outbox; конкурентный выбор записей использует `FOR UPDATE SKIP LOCKED`.

Точные правила и границы описаны в [технологическом стеке MVP](../mvp/TECH_STACK.md).

## Рассмотренные альтернативы

### TypeScript и grammY/Telegraf

Подход жизнеспособен, но не даёт преимуществ для текущей доменной модели, а выбранный Python-стек проще для быстрого создания бота, проверок инвариантов и будущих аналитических задач.

### Redis и Celery с первого релиза

Отклонено: добавляет отдельное хранилище, брокер и операционные отказы до появления нагрузки, которую PostgreSQL outbox не способен обработать.

### FastAPI и webhook

Отложено: MVP не имеет публичного HTTP API. Long polling уменьшает число внешних компонентов. Webhook можно добавить без изменения домена, когда этого потребует размещение или масштаб.

### Микросервисы

Отклонено: транзакционная экономика и небольшой объём системы выигрывают от единой базы и локальных транзакций. Границы модулей сохраняют возможность выделить сервис позже.

### MongoDB

Отклонено: реляционные ограничения, уникальность голосов, журнал операций и конкурентное резервирование естественно выражаются в PostgreSQL.

## Последствия

Положительные:

- одна транзакционная модель для экономики, заданий и outbox;
- минимум инфраструктуры для пилота;
- тестируемый домен без зависимости от Telegram;
- воспроизводимые зависимости и единый набор проверок;
- worker можно масштабировать горизонтально без смены очереди на раннем этапе.

Ограничения:

- PostgreSQL становится критической зависимостью и требует резервного копирования;
- долгие операции нельзя выполнять внутри Telegram handler;
- нужно явно контролировать жизненный цикл асинхронных сессий и не разделять одну сессию между конкурентными задачами;
- поставщик размещения и конкретная система error reporting пока не выбраны.
