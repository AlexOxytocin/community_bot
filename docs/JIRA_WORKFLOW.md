# Jira-lite процесс проекта CB

Обновлено: 2026-08-24. Каноническое решение: [ADR-0021](adr/0021-jira-lite-development.md).

## Назначение

Jira `CB` хранит продуктовый план, приоритет, критерии приёмки, зависимости,
статус и короткий итог значимой работы. Git хранит код, архитектуру, ADR и
долговременную документацию. Jira не должна превращаться в стенограмму команд.

## Когда нужна задача

Задача нужна для бага, функции, пользовательской истории, изменения runtime,
workflow, архитектуры или процесса разработки. Сначала используется подходящая
открытая задача; если её нет, создаётся новая.

Отдельная задача не нужна для опечатки, форматирования, локального исследования,
мелкого рефакторинга или исправления теста внутри уже открытой работы. Такое
изменение входит в текущую задачу или выполняется как `local`, если оно ничего не
меняет в поведении и плане продукта.

## Минимальное содержание

- зачем нужен результат;
- область и явное «не входит»;
- от двух до пяти проверяемых критериев приёмки;
- зависимости и существенные риски;
- способ проверки.

Не добавлять обязательные `plan.md`, `implementation-report.md`,
`final-review.md` и отдельные подзадачи на каждый слой.

## Статусы

Используется фактический простой маршрут Jira:

```text
К выполнению → В работе → Готово
                       ↘ На проверке (только когда проверка реально нужна)
```

Перед переходом нужно прочитать доступные transitions. В Jira отмечаются начало
работы, реальный блокер, решение с изменением scope и итог. Локальные команды,
промежуточные гипотезы и повторяющиеся результаты не комментируются.

## Git и delivery

Jira-задача не требует автоматически ветку, commit, push, PR, merge или deploy.

- Ветка полезна для многодневной, параллельной, рискованной или отдельно
  проверяемой работы.
- Commit создаётся только по прямому запросу или как согласованный checkpoint;
  при наличии задачи ключ добавляется в сообщение.
- PR нужен для независимого review, защиты `main` или release, а не для каждой
  локальной правки одного владельца.
- Deployment выполняется только по явному release/dev-delivery запросу. Push в
  `main` сам по себе не должен разворачивать приложение.

## Завершение

В итоговом комментарии достаточно:

```text
Результат:
Проверка:
Остаточный риск:
Не выполнялось:
```

`Готово` означает, что критерии задачи доказаны на заявленном уровне. Для
локальной разработки это не означает production deployment. Release-задача
может стать `Готово` только после требуемой публичной проверки и rollback proof.

## Подключение

Проект: `CB` (`Community_Bot`), team-managed software. Используется Atlassian
Rovo с правами чтения и записи. Учётные данные управляются подключением и не
хранятся в репозитории.
