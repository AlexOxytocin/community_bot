# Community Bot: рабочие инструкции Codex

## Базовый принцип

В этом репозитории используется штатный Codex без проектного оркестратора и
обязательных сторонних skills. По умолчанию одна задача выполняется одним
агентом. Субагенты допустимы только по прямому запросу пользователя.

Выбирай самый короткий безопасный путь к наблюдаемому результату. Масштаб
процесса, документации и тестов должен соответствовать риску изменения.

## Уровни работы

- `local` — анализ, прототип, неповеденческая документация, config/tooling и
  совсем малая правка внутри уже отслеживаемой работы. Новая Jira-задача,
  отдельная ветка, PR, независимый review и полный regression не нужны.
- `tracked` — основной режим для значимого бага, функции, пользовательской
  истории, изменения runtime или процесса. Нужны Jira-задача, критерии приёмки,
  затронутые проверки и короткий итог в Jira. Наличие задачи само по себе не
  требует отдельной ветки, commit, push, PR, merge или deployment.
- `release` — production deployment, миграция данных, безопасность, платежи,
  необратимая операция или высокий риск. Нужны план отката, релевантные
  интеграционные проверки и явная верификация результата.

Если запрос содержит значимое продуктовое или процессное изменение, используй
`tracked`. В остальных случаях начинай с `local` и повышай уровень только по
конкретному риску или прямому запросу пользователя.

## Jira и Git

- Jira — источник плана, приоритета, критериев и итогов значимой работы. Если
  подходящей открытой задачи нет, создай её перед tracked-реализацией.
- Не создавай отдельную задачу для опечатки, локального исследования, форматирования
  или мелкой части уже открытой задачи: зафиксируй её в существующей задаче.
- Не создавай ветку, commit, push, PR или merge только потому, что работа имеет
  уровень `tracked`. Для них нужен прямой запрос либо явный release/git-план.
- Сохраняй несвязанные пользовательские изменения и не смешивай их с задачей.
- Ключ Jira допустим в ветке, commit и PR, но не в runtime-идентификаторах кода.

## Разработка и проверки

- Сохраняй текущий стек и границы модулей. Структурное изменение требует ADR
  только когда действительно меняет долговременную архитектуру.
- Тестируй затронутое поведение. E2E, полный regression и порог покрытия нужны
  только когда это следует из риска или критериев приёмки.
- Integration-тест добавляется только для свойства реальной PostgreSQL:
  транзакции, блокировки и конкуренция, constraint/trigger, SQL-запрос,
  persistence/restart или миграция. Валидация, матрицы прав, DTO, ветвление
  application-кода и ошибки транспорта проверяются unit-тестами.
- Используй общий `database_url` из `tests/integration/conftest.py`: одна
  мигрированная template-БД и изолированный клон на тест. Не запускай контейнер
  или `alembic upgrade head` из обычного integration-теста.
- Не дублируй happy path между domain, application, Web API и browser. Для
  вертикального среза оставляй один DB-backed путь и только уникальные
  DB-инварианты. Не импортируй новые helpers из `test_*.py`; общие builders
  помещай в `conftest.py` или модуль поддержки без префикса `test_`.
- Бюджет suite на штатной локальной машине: integration до 120 секунд, полный
  pytest до 240 секунд. При превышении сначала устрани повторную подготовку,
  параметризацию или дубли, а не повышай лимит.
- Не создавай `plan.md`, `implementation-report.md`, `final-review.md` и другие
  процессные артефакты для local-задач.
- Не подключай LLM там, где достаточно детерминированного кода.

## Локальная разработка Telegram Mini App

- Этот UI является Telegram Mini App, а не сайтом. Не подменяй проверку Mini
  App проверкой landing page или корня публичного домена.
- Промежуточные UI-этапы по умолчанию разрабатывай и показывай на локальном
  backend Mini App по `http://127.0.0.1:8000`, в Telegram-совместимом мобильном
  viewport. До отдельного согласования не выкладывай каждый этап на сервер.
- Для реалистичной локальной приёмки используй актуальный проверенный snapshot
  серверной PostgreSQL из `%LOCALAPPDATA%\CommunityBot\snapshots`, восстановленный
  в отдельный контейнер `community-bot-ui-local-postgres`, volume
  `community_bot_ui_local_pgdata` и порт `127.0.0.1:55432`. Не затрагивай обычную
  dev-БД проекта.
- Не скачивай БД заново в каждой задаче. Переиспользуй текущий локальный snapshot;
  обновляй его только по прямому запросу пользователя либо когда изменившаяся
  схема или необходимые данные делают текущий snapshot непригодным.
- Локальный review-вход допустим только при `ENVIRONMENT=development`, loopback
  origin и явном `LOCAL_REVIEW_TELEGRAM_USER_ID`. Production Telegram `initData`,
  HTTPS и Secure `__Host-` cookie должны оставаться fail-closed.
- Cookie локального review изолирована по профилям браузера. Если локальный Mini
  App показывает истёкшую сессию во встроенном браузере или новом профиле,
  открой в этом же браузере `http://127.0.0.1:8000/local-review` один раз, затем
  верни исходный URL. Не подменяй этим production-аутентификацию.
- Snapshot и локальные session-данные не помещай в git, Jira, документацию или
  логи. Для доказательств используй только путь вне репозитория, SHA-256,
  миграционную revision, агрегатные количества и результаты инвариантов.
- Каждый UI-этап сначала предъявляй через локальный Mini App и сверяй с
  пользователем. Commit, push и server deployment выполняй только по прямому
  запросу или после явного согласования финального релиза.

## Production deployment Telegram-продукта

- Это Telegram-приложение, запускаемое через бота, а не публичное web-приложение.
  Deployment означает доставку backend/runtime и Telegram Mini App, доступного
  из production-бота. Корень `https://allo.godmodetools.com/`, его redirect и
  marketing/landing page не являются продуктовым экраном или acceptance URL.
- Никогда не открывай и не используй корень `allo.godmodetools.com` для проверки
  интерфейса, маршрутов или успешности Telegram-релиза. Не анализируй landing
  page и не меняй его nginx/redirect в рамках Telegram-задачи без отдельного
  прямого запроса пользователя.
- `https://allo.godmodetools.com/readyz` разрешён только как инфраструктурный
  health-check exact release, PostgreSQL, migration и worker heartbeat. Зелёный
  `/readyz` не доказывает, что Telegram Mini App запускается и работает.
- Production UI acceptance выполняй только реальным запуском Mini App из
  production-бота в Telegram с настоящим `initData` и Telegram-совместимым
  мобильным viewport. Проверяй вход через бота, авторизацию и изменённый экран.
  Перед этим прочитай Telegram rule и используй только канонический wrapper;
  не читай чаты и не отправляй сообщения без прямого запроса.
- Если доступной production Telegram-сессии нет, прямо сообщи: runtime
  развёрнут, но Telegram acceptance не выполнен. Не подменяй её обычным
  браузером, landing page, прямым URL, локальным review-входом или моками и не
  называй Telegram deployment полностью проверенным.

## Release preflight и ограничение импровизации

- До начала реализации выполни `git fetch` и сравни `HEAD` с `origin/main`.
  Не начинай значимую реализацию на отстающей ветке: сначала перенеси работу на
  актуальный `main`, чтобы не разрешать большие конфликты непосредственно перед
  release.
- До server mutation зафиксируй только измеренные значения: полный SHA через
  `git rev-parse`, running image/revision, live Alembic head, фактический Compose
  package из labels работающих контейнеров, список services, backup path и
  rollback target. Не угадывай SHA, path, service или release state.
- Если release меняет Alembic head, fast deploy запрещён. Сначала должен
  существовать один проверенный migration/cutover path с остановкой writers,
  fresh backup, isolated restore drill, миграцией, rollback до mutation и exact
  readiness. Если такого пути нет, не импровизируй на production: сначала
  реализуй и локально проверь переиспользуемый release tool/runbook.
- Не передавай production-скрипт через `ssh ... bash -s`/stdin. Команда внутри
  такого скрипта может прочитать остаток stdin. В частности, для Compose
  one-shot запрещён `docker compose run` без `-T`. Выполняй versioned script из
  файла с проверенным digest; перед mutation проверь его syntax/dry preflight.
- До остановки процессов `docker compose config --services` обязан подтвердить
  точный production package и services `postgres`, `migrate`, `worker`, `web`.
  Не используй `/opt/community-bot/current` или legacy `active.json`, пока их
  соответствие фактически работающим container labels не доказано.
- После двух ошибок preflight/quoting останови попытки и не продолжай собирать
  ad-hoc shell-команды. Устрани причину локально и переходи к одному проверенному
  сценарию. Целевой бюджет release до mutation — 10 минут; если безопасный путь
  за это время не подтверждён, сервер не изменяй и сообщи blocker.
- После mutation приоритет — немедленно вернуть healthy runtime или выполнить
  заранее подготовленный rollback. Эксперименты, исследование edge/landing и
  несвязанные исправления во время cutover запрещены.

## Внешние системы и безопасность

- Любое внешнее изменение требует ясного намерения пользователя. Перед
  повтором проверяй состояние и исключай дубликат.
- Для Telegram сначала прочитай `C:\Users\User\.codex\rules\telegram.md` и
  используй канонический wrapper. Не читай чаты и не отправляй сообщения без
  прямого запроса.
- Секреты, токены, cookies, OTP, Telegram sessions и приватные учётные данные
  не помещаются в git, Jira, документацию или логи.
- Web delivery считается готовой только после deployment и проверки публичного
  URL. Локальный build или тест — это локальный результат, не deployment.

## Коммуникация

Пиши пользовательские отчёты по-русски. В финале укажи результат, проверку,
оставшийся риск и внешние действия, которые фактически не выполнялись.
