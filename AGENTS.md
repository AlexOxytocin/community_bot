# Community Bot: рабочие инструкции Codex

## Базовый принцип

В этом репозитории используется штатный Codex без проектного оркестратора и
обязательных сторонних skills. По умолчанию одна задача выполняется одним
агентом. Субагенты допустимы только по прямому запросу пользователя.

Выбирай самый короткий безопасный путь к наблюдаемому результату. Масштаб
процесса, документации и тестов должен соответствовать риску изменения.

## Уровни работы

- `local` — анализ, прототип, неповеденческая документация, config/tooling и
  совсем малая правка внутри уже отслеживаемой работы. Новая Jira-задача,
  отдельная ветка, PR, независимый review и полный regression не нужны.
- `tracked` — основной режим для значимого бага, функции, пользовательской
  истории, изменения runtime или процесса. Нужны Jira-задача, критерии приёмки,
  затронутые проверки и короткий итог в Jira. Наличие задачи само по себе не
  требует отдельной ветки, commit, push, PR, merge или deployment.
- `release` — production deployment, миграция данных, безопасность, платежи,
  необратимая операция или высокий риск. Нужны план отката, релевантные
  интеграционные проверки и явная верификация результата.

Если запрос содержит значимое продуктовое или процессное изменение, используй
`tracked`. В остальных случаях начинай с `local` и повышай уровень только по
конкретному риску или прямому запросу пользователя.

## Jira и Git

- Jira — источник плана, приоритета, критериев и итогов значимой работы. Если
  подходящей открытой задачи нет, создай её перед tracked-реализацией.
- Не создавай отдельную задачу для опечатки, локального исследования, форматирования
  или мелкой части уже открытой задачи: зафиксируй её в существующей задаче.
- Не создавай ветку, commit, push, PR или merge только потому, что работа имеет
  уровень `tracked`. Для них нужен прямой запрос либо явный release/git-план.
- Сохраняй несвязанные пользовательские изменения и не смешивай их с задачей.
- Ключ Jira допустим в ветке, commit и PR, но не в runtime-идентификаторах кода.

## Разработка и проверки

- Сохраняй текущий стек и границы модулей. Структурное изменение требует ADR
  только когда действительно меняет долговременную архитектуру.
- Тестируй затронутое поведение. E2E, полный regression и порог покрытия нужны
  только когда это следует из риска или критериев приёмки.
- Не создавай `plan.md`, `implementation-report.md`, `final-review.md` и другие
  процессные артефакты для local-задач.
- Не подключай LLM там, где достаточно детерминированного кода.

## Внешние системы и безопасность

- Любое внешнее изменение требует ясного намерения пользователя. Перед
  повтором проверяй состояние и исключай дубликат.
- Для Telegram сначала прочитай `C:\Users\User\.codex\rules\telegram.md` и
  используй канонический wrapper. Не читай чаты и не отправляй сообщения без
  прямого запроса.
- Секреты, токены, cookies, OTP, Telegram sessions и приватные учётные данные
  не помещаются в git, Jira, документацию или логи.
- Web delivery считается готовой только после deployment и проверки публичного
  URL. Локальный build или тест — это локальный результат, не deployment.

## Коммуникация

Пиши пользовательские отчёты по-русски. В финале укажи результат, проверку,
оставшийся риск и внешние действия, которые фактически не выполнялись.
