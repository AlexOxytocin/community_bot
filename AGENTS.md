## Язык

- Русский — обязательный язык всей смысловой документации, Jira-комментариев, планов, отчётов, проверок и пользовательских сообщений.
- Английский используется для кода, идентификаторов, полей API и базы данных, ключей конфигурации, переменных окружения, логов, сообщений об ошибках во время выполнения, путей, команд и точных названий внешних сущностей.
- Неполный перевод смыслового артефакта является дефектом и блокирует публикацию в Jira.

## Главные правила

- Jira `CB` — источник задач, статусов, приоритетов, связей, блокирующих зависимостей и критериев приёмки.
- Любой баг, функция, пользовательская история, изменение runtime-поведения,
  workflow или процесса разработки сначала заводится или выбирается в Jira `CB`;
  реализация без ключа Jira запрещена.
- Git-документация — источник долговременных продуктовых, архитектурных и процессных решений.
- Не использовать ключ Jira в именах, работающих во время выполнения. Допустимо: `task/CB-12`, запрос на слияние и артефакты задачи. Недопустимо: `Cb12Handler`, `CB12_TOKEN`, `test_cb_12.py`.
- Одна Jira-задача — одна ветка `task/<ISSUE-KEY>`. Не выполнять коммиты задачи напрямую в `main`.
- Каждая ветка, созданная для Jira-задачи, должна пройти маршрут: локальные
  проверки → commit → push → pull request → CI/review → merge в `main`, если
  gate не заблокирован. Для задачных веток это постоянное намерение владельца.
- Fast lane уровня `1B` ускоряет план, отчёт и ревью, но не отменяет Jira-задачу
  и ветку `task/<ISSUE-KEY>`.
- Изменения должны соответствовать утверждённой области и сохранять несвязанные пользовательские правки.
- Не утверждать, что работа завершена, пока не закрыты критерии приёмки, проверки, документация и обязательная проверка выбранного уровня риска. Для уровня `1B` по ADR-0010 это compact bugfix note и короткая diff-проверка; для уровней 2–3 — `final-review.md`.
- Не хранить секреты, токены, куки, данные сессий или приватные учётные данные в git, Jira, документации, артефактах задач и MemPalace.
- Внешние изменения выполняются только при ясном намерении пользователя. Для
  задачных веток постоянное намерение владельца уже включает commit, push, PR и
  merge после успешных gates. Перед повтором потенциально частично выполненной
  операции проверить внешнее состояние и исключить дубликат.

- Адрес сайта получать через установленное подключение Atlassian и не дублировать в публичной документации.
- Проект: `CB` (`Community_Bot`), доска `3`.
- Анализ без изменений выполняется по запросу без дополнительного подтверждения.
- Перед переходом получать доступные переходы конкретной задачи и использовать только точные названия, возвращённые Jira.

## Telegram

- Для операций с пользовательским аккаунтом использовать `C:\Users\User\.codex\tools\telegram.ps1` и каноническое подключение `C:\Users\User\jarvis\integrations\telegram`.
- Для многопользовательских live-проверок доступен второй локальный профиль
  `tg-test`; проверять его безопасной командой
  `C:\Users\User\.codex\tools\telegram.ps1 -Profile tg-test probe`. В проект
  фиксируется только ярлык профиля и результат probe, без session string,
  телефона, Telegram ID, сообщений и списка чатов.
- Не копировать пользовательскую сессию Telegram или учётные данные в этот проект.
- Не читать чаты, не скачивать медиафайлы и не отправлять сообщения без явного запроса на конкретное действие.
- Перед повторной отправкой проверять последние сообщения и исключать дубликат.
- Для исправлений Telegram-интерфейса, runtime-поведения бота, карточек,
  callback-кнопок, регистрации, баланса, профилей и пользовательских сценариев
  можно отдельно заявлять локальную готовность к PR после output-driven тестов,
  fake Bot API или другого достаточного локального доказательства. Нельзя писать
  «исправлено на рабочем экземпляре», закрывать production gate или переводить
  задачу в финальный `Done`, если свежая проверка в живом чате не выполнена и
  фактический ответ бота не подтверждает исправление.
- Перед живой Telegram-проверкой рабочего экземпляра обязательно выполнить
  deployment актуального проверенного release на сервер по
  `docs/operations/PILOT_RUNBOOK.md`. Проверка локального кода, CI и
  опубликованного image без server deploy не является проверкой рабочего
  экземпляра. Несколько малых Telegram-исправлений можно проверять пакетно на
  этапе release acceptance, если отчёт честно фиксирует, что live gate ещё не
  закрыт.
- Будущий токен Bot API должен поступать через переменные окружения или хранилище секретов и никогда не попадать в коммиты.

## Память

- Отдельный MemPalace проекта: `C:\Users\User\.mempalace\palaces\community_bot`, область `community_bot`.
- Документация в git является источником истины; MemPalace — только поисковый индекс.
- Индексировать долговременные несекретные выводы. Не индексировать `.env`, учётные данные, сессии, необработанные приватные чаты, результаты сборки и временные файлы.

## Разработка

- Использовать стек из `docs/mvp/TECH_STACK.md` и ADR-0005; его структурное изменение требует нового ADR и явного решения владельца.
- Для первой версии предпочитать небольшой модульный монолит и явные границы транспортного, прикладного, доменного и инфраструктурного слоёв.
- Все эксплуатационные и вспомогательные скрипты проекта должны быть на Python.
  Shell-скрипты в репозитории не добавлять и не поддерживать; shell допустим
  только как отдельные команды в документации, CI YAML или внутри контейнера,
  когда вызывается внешняя утилита. Исключение составляют два узких root-owned
  release wrapper-а `ops/github_deploy_entrypoint.sh` и
  `ops/deploy_self_hosted.sh`, уже закреплённые ADR-0011/ADR-0012; расширение
  этого исключения требует нового ADR и явного решения владельца.
- Не разрешать продуктовые вопросы `TBD` молча в коде; сначала обновить журнал решений.
- Детерминированные операции, валидацию, права и вычисления реализовывать кодом; LLM применять только там, где нужна работа с естественным языком или неоднозначностью.
- Для изменяющих операций разделять предварительную проверку, предпросмотр и применение, обеспечивать идемпотентность и защиту от повторной обработки обновлений Telegram.
- Тесты и документация изменяются вместе с поведением.
